### 🔴 초당 1건 — 이 프로젝트에서 실제로 가장 크게 터진 문제

KIS는 **앱키 하나당 초당 1건**만 허용합니다(`EGW00201` 초당 거래건수 초과). 계획 단계에서는 "연결이 되느냐"만 위험으로 봤지 **호출 빈도**는 위험 목록에 없었습니다.

기능이 늘수록 곳곳에서 따로 터졌습니다 — 주문(시세+매수가능+hashkey+주문 = 4연속), 인기 종목, 분봉 차트(최대 14연속), 배당 조회. 새로고침 두 번이면 걸릴 정도였습니다.

**해결**: 기능별로 재시도·캐시를 따로 넣던 방식을 그만두고, 모든 KIS 호출이 공통으로 거치는 `callKis`에 **전역 큐**(`reserveKisSlot`, 최소 1,100ms 간격)를 하나 두는 것으로 근본 해결했습니다.

| 방어선 | 내용 |
|---|---|
| 전역 큐 | 모든 호출을 1.1초 간격으로 직렬화 |
| 라우트별 TTL 캐시 | 인기 종목 15초 · 차트 60초(일봉)·180초(분봉) · 배당·재무 60분 |
| inflight 합치기 | 같은 종목 동시 요청은 한 번만 호출하고 결과를 공유 |
| 토큰 3계층 캐시 | 인메모리 → `kis_tokens` → 발급 |
| 리전 고정 | `vercel.json`에 `icn1` — 큐 때문에 늘어난 응답 시간을 왕복 지연 단축으로 상쇄 |

> ⚠️ **큐가 새 문제를 만들었습니다.** 분봉 차트처럼 한 요청에서 14번을 연속 호출하면 큐 간격만으로 15초가 넘습니다. 그래서 `/api/chart`에 `maxDuration = 45`를 두고 40초 데드라인에서 남은 페이지를 포기하도록 했습니다.

> 🔄 **2026-08-06 변경.** 흐름 B(계좌 화면)는 더 이상 KIS 계좌 잔고 조회를 직접 쓰지 않습니다. 공용 모의계좌라 다른 방문자의 잔고가 섞여 보이는 문제 때문에, `orders` 기준 내 주문만 합산하고 보유 종목의 현재가만 KIS에서 조회합니다. 계좌 잔고 조회는 이제 예외 2.5(주문 전 실제 예수금 확인)에서만 쓰입니다. ([[../02_Domain/03_workflow|업무 흐름]] 흐름 B)

### 🔴 프롬프트 공통 금지 규칙

모든 프롬프트에 다음을 명시합니다.

```
- 특정 종목의 매수·매도를 권유하지 마십시오.
- 목표 가격이나 수익률을 예측하지 마십시오.
- 사용자의 판단이 옳거나 틀렸다고 평가하지 마십시오.
- 숫자가 무엇을 의미하는지 설명하는 데까지만 답하십시오.
```

**이유 2가지**

| 이유 | 설명 |
|---|---|
| 법적 | 특정 종목 매수 권유는 유사투자자문 영역에 접근합니다 |
| 목적 | AI 의견을 따라가면 **사용자가 자기 판단을 설명하게 만든다**는 목적과 정반대가 됩니다 |

> [[../05_Scope/02_definition_of_done|완료 기준]]에서 AI 응답 30건에 권유 표현이 0건인지 검사합니다.

### 출력 형식

| 항목 | 계획 | 🔄 실제 |
|---|---|---|
| 응답 형식 | 일반 텍스트 (JSON 강제하지 않음) | **`제목\|내용` 파이프 형식을 엄격히 강제** |
| 길이 제한 | 프롬프트에서 "4문장 이내" 지시 | 구획당 2~3문장 × 2~4구획, `maxOutputTokens: 2048` |
| 스트리밍 | 사용하지 않음 | 동일 |
| 타임아웃 | 8초 (Vercel 제한 10초보다 이르게) | 동일 (8초) |

> 🔄 **"JSON을 강제하지 않는다"는 유지했지만 형식은 강제하게 됐습니다.** 자유 텍스트로 받아보니 문단이 통으로 나와 화면에서 읽기 어려웠습니다. JSON은 모델이 깨뜨리면 파싱이 통째로 실패하지만, `제목|내용` 한 줄 형식은 **일부만 깨져도 나머지를 살릴 수 있어** 절충안으로 택했습니다.
>
> 그래도 형식이 깨질 때를 대비해 **형식 파싱 실패 → 빈 줄 기준 문단 분리 → 통짜 한 덩어리** 순의 폴백 체인을 뒀습니다. **글이 사라지는 경우는 없습니다.**

> **스트리밍을 쓰지 않는 이유**: 구현 시간이 늘고, 실패 처리가 복잡해집니다. 스트리밍 없이도 충분히 빠릅니다. 4일 일정에서 체감 개선을 위한 복잡도는 사치입니다.

> ⚠️ **AI 응답 캐시(같은 종목 5분 재사용)는 만들지 않았습니다.** Should Have에 있었고, 자동 호출을 하지 않고 버튼을 눌렀을 때만 부르는 것으로 대부분 해결되어 필요가 크지 않았습니다.

| service role key | ~~🔴 **사용하지 않습니다**~~ 🔄 **사용합니다** (아래) |

### ~~service role key를 쓰지 않는 이유~~ 🔄 결국 썼습니다

**계획**은 이랬습니다. `kis_tokens`와 `event_logs`는 RLS 정책이 없어 anon key로 접근할 수 없으니, 이 두 테이블만 `security definer` 함수로 여는 것입니다.

```sql
-- 계획했던 함수 (❌ 만들지 않았습니다)
create or replace function get_kis_token()
returns table (access_token text, expires_at timestamptz)
language sql security definer
as $$ select access_token, expires_at from kis_tokens where id = 1 $$;
```

service role key가 유출되면 **모든 테이블에 무제한 접근**이 열립니다. 함수로 제한하면 그 함수가 하는 일만 열립니다. **이 논리는 지금도 맞습니다.**

> 🔄 **하지만 함수는 만들지 않았고, service role key를 씁니다.** DB에 사용자 정의 함수가 하나도 없습니다. `lib/supabase/admin.ts`가 `SUPABASE_SERVICE_ROLE_KEY`로 클라이언트를 만들고, 사용처는 **계획한 2곳이 아니라 5곳**입니다.
>
> | 무엇을 | 세션 키로는 왜 안 되는가 |
> |---|---|
> | `kis_tokens` 읽기·쓰기 (`lib/kis.ts`) | 정책이 없어 접근 자체가 막힘. **로그인 안 한 방문자도 시세를 봐야** 하므로 세션이 없을 수 있음 |
> | `event_logs` 쓰기 (`lib/events.ts`) | 동일. **로그인 이전 단계의 이벤트**(토큰 갱신 실패 등)도 기록해야 함 |
> | `user_wallets` upsert (`/api/order`) | 예산 지급은 서버만 해야 하므로 `insert`·`update` 정책을 일부러 두지 않았음 |
> | `stocks` 조회 (`/api/disclosures`, `/api/ai/explain`) | **공개 데이터라 세션 키로도 됨.** admin 클라이언트를 습관적으로 재사용한 것 — 줄일 수 있는 부분 |
>
> ⚠️ **원래 계획이 "시간이 부족하면 쓰고, 그 경우 발표에서 한계로 명시한다"였습니다.** 교체를 못 했으므로 **명시하는 쪽 약속을 지킵니다.**
>
> **실제 위험 크기**: 키는 서버 환경변수에만 있고 `NEXT_PUBLIC_` 접두사가 없어 브라우저 번들에 들어가지 않습니다. **키 자체가 새는 경로는 없습니다.** 문제는 서버 코드에 버그가 생겼을 때 RLS가 막아주지 못한다는 것 — 방어선이 2겹에서 1겹이 됩니다. 자세한 내용은 [[01_data_structure|데이터 구조]] 7절.
>
> 🔴 **`lib/supabase/admin.ts`에는 `import "server-only"` 가드가 없었습니다.** "client에서 import하지 마세요"라는 주석만 있고 강제가 없어서, 실수로 클라이언트 컴포넌트가 가져다 쓰면 키가 번들에 들어갈 수 있었습니다. 8/7에 형제 파일(`lib/dart.ts`·`news.ts`·`portfolio.ts`)과 같은 가드를 추가했습니다.

### 🆕 그 밖의 환경변수

| 환경변수 | 용도 | 계획에 있었나 |
|---|---|---|
| `SUPABASE_SERVICE_ROLE_KEY` | 위 4곳 | ❌ "안 쓴다"고 했던 것 |
| `DART_API_KEY` | DART 공시 조회 | ❌ 8/7 추가 |

## 6. 소스별 실패가 서비스에 미치는 영향

| 소스 실패 | 계좌 화면 | 종목 화면 | 주문 | 회고 화면 |
|---|---|---|---|---|
| KIS 실패 | ⚠️ **보유목록·예산은 표시**, 현재가만 `—` | ❌ 시세 불가 | ❌ | ⚠️ 현재가 대비만 빠짐 |
| Gemini 실패 | ⚠️ 숫자만 표시 | ⚠️ 숫자만 표시 | ✅ **영향 없음** | ⚠️ 목록만 표시 |
| Supabase 실패 | ❌ **아무것도 못 그림** | ❌ 종목 검색 불가 | ❌ | ❌ |
| 🆕 DART·뉴스 실패 | ✅ 영향 없음 | ⚠️ 공시뉴스 탭이 "최근 공시·뉴스가 없습니다" | ✅ 영향 없음 | ✅ 영향 없음 |
| 🆕 배당·재무 실패 | ✅ 영향 없음 | ⚠️ 해당 영역만 사라짐(캐시 있으면 stale 표시) | ✅ 영향 없음 | ✅ 영향 없음 |

> 🔄 **KIS·Supabase 행이 계획과 반대였습니다.** 계좌 화면을 `orders` 기준으로 바꾸면서 의존 방향이 뒤집혔는데 이 표만 옛날 상태로 남아 있었습니다.
>
> - **KIS 실패**: `/api/account`가 실패를 삼키고 목록·예산을 200으로 반환합니다. 현재가만 `null`이 되므로 ❌가 아니라 ⚠️입니다.
> - **Supabase 실패**: 이제 계좌 화면이 전적으로 `orders`에서 나오므로 ⚠️가 아니라 **❌**입니다.

### 🔴 이 표에서 읽어야 할 것

**Gemini가 죽어도 주문과 근거 기록은 동작합니다.** 주문 경로에 AI를 넣지 않은 결과입니다.

**부가 데이터(공시·뉴스·배당·재무)는 전부 실패해도 조용히 비워집니다.** 각 함수가 throw하지 않고 빈 배열을 돌려주기 때문입니다.

**회고 화면은 KIS가 죽어도 대부분 동작합니다.** 저장된 데이터만으로 그려지기 때문입니다. → **발표 시연의 최종 안전판은 회고 화면입니다.**

🔴 **바꿔 말하면 Supabase가 유일한 단일 장애점입니다.** 계획 시점에는 KIS가 그 자리였는데, 계좌를 `orders` 기준으로 옮기면서 의존이 Supabase로 모였습니다.
