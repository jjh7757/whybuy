- 작성일: 2026-08-06
- 선행 문서: `plan/KIS-Agent-Notes/05_Scope/01_mvp_scope`

## 1. 진행 방식 — 혼합형 (Waterfall + Agile)

| 미리 고정할 것 | 반복해서 실험할 것 |
|---|---|
| 4일 기간과 발표일 | AI 해석의 표현 방식 |
| 목적과 성공 기준 | 회고 코멘트 프롬프트 |
| 화면 3개 구성 | 근거 선택지 문구 |
| 테이블 6개 | 첫 화면 안내 문구 |
| `/api/order` 14단계 순서 | |
| 자격증명·개인정보 원칙 | |

기간이 4일이고 **버퍼가 사실상 없습니다.** 구조는 Waterfall처럼 먼저 확정하고, **프롬프트만 Agile처럼 반복**합니다. 구조 변경 비용은 크고 프롬프트 변경 비용은 작기 때문입니다.

---

## 2. 핵심 가정

```
주문 직전에 판단 근거를 반드시 적게 하고
그 근거들을 한 화면에 모아 보여주면
사용자가 자신의 과거 매매 판단을 설명할 수 있게 될 것입니다.
```

**아직 검증되지 않았습니다.** MVP의 목적은 이 가정을 확인하는 것입니다.

---

## 3. MVP 사용자 흐름

```
접속 → 무엇을 하는 서비스인지 이해
→ 내 계좌 상황 확인 (AI 해석)
→ 종목 검색 → 시세 확인 (AI 해석)
→ 수량 입력 → 근거 선택 (필수)
→ 주문 실행
→ 회고 화면에서 방금 근거 확인
→ 지난 근거들을 되돌아봄 (AI 코멘트)
```

**이 흐름이 끝까지 이어지는 것이 MVP의 정의입니다.** 중간에 끊기면 가정을 검증할 수 없습니다.

### 4.2 Should Have

| 기능 | 예상 | 왜 Must가 아닌가 |
|---|---:|---|
| **AI-3 용어 설명** | 1h | AI 기능은 이미 2개입니다. 없어도 REQ-02를 만족합니다 |
| `security definer` 함수로 토큰 접근 | 0.7h | service role key를 서버 전용으로 쓰면 당장은 동작합니다 |
| AI 해석 5분 캐시 | 0.5h | 자동 호출을 안 하는 것만으로 대부분 해결됩니다 |
| 근거 유형별 필터·정렬 | 1h | 4일치 데이터는 정렬 없이도 한눈에 보입니다 |

> 🔴 **`AI-3 용어 설명`이 Should 1순위입니다.** Day 4에 버퍼가 남으면 가장 먼저 넣습니다. **KIS에 의존하지 않는 유일한 기능이라 시연 안전판이 되기 때문**입니다. 다만 시연 효과를 위해 Must로 올리지는 않습니다.

|---|---|

| **매도 주문** | 근거 유형 체계가 따로 필요(손절·차익실현). 매수만으로 성공 기준을 측정할 수 있습니다 |
| **체결 조회** | 성공 기준과 무관. 발표에서 "주문 접수까지"라고 명시합니다 |
| 실전 투자 계좌 | 실제 자금 위험 |
| 종목 추천·목표가 | 유사투자자문 영역이고 목적과 반대 방향 |

| 차트·기술적 분석 | 4일에 들어가지 않고 판단 근거와 무관 |
| 뉴스·공시 수집 | 외부 데이터 범위가 큽니다 |
| 실시간 알림·스케줄러 | Vercel에 상주 프로세스가 없습니다 |
| 백테스팅 | 별도 프로젝트 규모 |

## 5. 시간 배분

```
가용 시간               약 28h   (Day1 5h + Day2 8h + Day3 8h + Day4 7h)
──────────────────────────────
Must 개발               -22.3h
제출 문서 (README·범위)  -2h
발표자료 + 리허설         -2h
──────────────────────────────
버퍼                    약 1.7h
```

> Google 로그인(Supabase Auth) + 가상 예산 기능이 원래 계획(익명 쿠키, +0.6h)보다 더 늘어 **+1.3h**가 되었습니다. 지속 가능한 서비스를 위해 쿠키 대신 실제 계정을 쓰기로 한 결정에 따른 비용입니다. 버퍼가 3h→1.7h로 줄었지만, Should 항목(AI-3 용어 설명 등)을 포기하면 즉시 회수할 수 있는 여유이므로 여전히 관리 가능합니다.

### 🔴 버퍼가 1.7시간뿐인 이유

**개발 종료 다음 날이 발표일이고, Day 1이 이미 반나절입니다.**

**대응: 버퍼를 날짜가 아니라 기능에서 확보합니다.**

```
Day 3 종료 시점에 이미 시연 가능한 상태를 완성한다
→ Day 4는 검수 + 문서 + 발표 준비만
```

상세는 [[../06_WBS/02_milestones|4일 마일스톤]]에 있습니다.

## 7. Scope Creep 방어

새 기능이 떠오르면 아래 3개를 전부 만족하지 않으면 `Could` 또는 `Won't`로 보냅니다.

```
1. 이 기능이 없으면 핵심 가정을 검증할 수 없는가?
2. 이 기능이 없으면 MVP 사용자 흐름이 끊기는가?
3. Must 합계가 22.3h를 넘지 않는가?
```

**4일 프로젝트에서 가장 흔한 실패는 기능 부족이 아니라 미완성입니다.**

### 이번에 특히 유혹적일 기능

| 유혹 | 왜 참아야 하는가 |
|---|---|
| 자연어 채팅창 | "AI 서비스답다"는 인상 때문에 끌립니다. 하지만 4h가 들고, 폼보다 정확도가 낮으며, **웹으로 옮긴 이유와 정반대**입니다 |
| 실시간 차트 | 화려하지만 판단 근거와 무관합니다 |
| 로그인 방식 확대 (이메일 가입, 프로필 편집 등) | Google OAuth 1개로 REQ-03·04를 충분히 만족합니다. 여러 로그인 수단을 두는 건 4일 범위 밖입니다 |
| 종목 추천 AI | 가장 그럴듯해 보이지만 유사투자자문 위험이고 목적과 반대 방향입니다 |
| 디자인 다듬기 | 끝이 없습니다. **Day 4 오후에만 손댑니다** |
