## 1. 진행 방식 — 혼합형 (Waterfall + Agile)

| 미리 고정할 것 | 반복해서 실험할 것 |
|---|---|
| 4일 기간과 발표일 | AI 해석의 표현 방식 |
| 목적과 성공 기준 | 회고 코멘트 프롬프트 |
| 화면 3개 구성 | 근거 선택지 문구 |
| 테이블 6개 | 첫 화면 안내 문구 |
| `/api/order` 14단계 순서 | |
| 자격증명·개인정보 원칙 | |

기간이 4일이고 **버퍼가 사실상 없습니다.** 구조는 Waterfall처럼 먼저 확정하고, **프롬프트만 Agile처럼 반복**합니다. 구조 변경 비용은 크고 프롬프트 변경 비용은 작기 때문입니다.

---

## 2. 핵심 가정

```
주문 직전에 판단 근거를 반드시 적게 하고
그 근거들을 한 화면에 모아 보여주면
사용자가 자신의 과거 매매 판단을 설명할 수 있게 될 것입니다.
```

**아직 검증되지 않았습니다.** MVP의 목적은 이 가정을 확인하는 것입니다.

---

## 3. MVP 사용자 흐름

```
접속 → 무엇을 하는 서비스인지 이해
→ 내 계좌 상황 확인 (AI 해석)
→ 종목 검색 → 시세 확인 (AI 해석)
→ 수량 입력 → 근거 선택 (필수)
→ 주문 실행
→ 회고 화면에서 방금 근거 확인
→ 지난 근거들을 되돌아봄 (AI 코멘트)
```

**이 흐름이 끝까지 이어지는 것이 MVP의 정의입니다.** 중간에 끊기면 가정을 검증할 수 없습니다.

### 4.2d 8/7 — 매도 주문 추가 (Won't Have 항목을 뒤집음)

사용자가 직접 요청했습니다: "종목 판매하는 기능도 넣어줘." 4.4절의 원래 제외 이유(매도 근거 유형 체계가 매수와 완전히 다름 — 손절·차익실현은 저평가·실적·업황 같은 매수 근거와 대응되지 않음)는 여전히 유효한 지적이었지만, 근거 유형만 따로 두면 해소되는 문제였지 영구히 못 만들 이유는 아니었습니다.

| 기능 | 왜 추가했나 | 왜 Must는 아니었나 |
|---|---|---|
| 매도 전용 근거 5종(손절/익절/목표가 도달/판단이 바뀜/그냥 감) | 매수 근거(저평가·실적·업황·뉴스·배당·감)와 성격이 달라 새로 만듦(`lib/rationale.ts`) | 매수만으로도 성공 기준(판단 근거 기록)은 측정 가능 |

| 보유수량·가상예산 계산 재작성(`lib/portfolio.ts`) | 기존엔 "체결된 매수 수량 합계 = 보유 수량"이라고 가정하고 있었음(주석에 명시돼 있었음). 매도가 생기면서 평단가는 매도해도 안 바뀌게(평균 매입단가 방식), 매도 체결분은 예산에 돌려주게, "지금 팔 수 있는 수량"(대기중인 매도 잔량 제외)을 따로 계산하게 바꿈 | 이 계산 없이는 매도 자체가 성립하지 않아 선택의 여지가 없었음 |

| 보유 종목에서만 노출되는 매수/매도 토글(TradeFlow) | 안 가진 종목을 팔 수 있게 보여주면 눌러도 막힐 버튼이 됨 | 화면 구성일 뿐 새 판단 재료는 아님 |
| 계좌 화면 보유 종목 클릭 → 해당 종목 화면 이동 | 매도 토글이 생기면서 "내 계좌"에서 보유 종목을 보고 바로 팔 수 있는 길이 필요해짐 | 화면 이동 편의 기능일 뿐 새 판단 재료는 아님 |

> 🔴 **잠재 버그를 하나 발견해 같이 고쳤습니다.** 중복 주문 방어(예외 2.6, 60초 내 동일 종목·동일 수량)가 `side`를 안 보고 있었습니다. 매도가 없을 때는 문제가 안 됐지만, 매도가 생기면 "5주 매수" 직후 "5주 매도"를 같은 주문의 중복으로 오인해 정상적인 매도를 막았을 것입니다. `side`를 조건에 추가했습니다.
>
> **부작용**: `orders.side` 컬럼은 이미 존재했지만(기본값 `'buy'`) 지금까지 실제로 `'sell'`이 들어간 적은 없었습니다. `getMyPortfolio`(`lib/portfolio.ts`)의 반환값에 `availableToSell`(종목코드별 매도 가능 수량)이 추가돼 `/api/budget` 응답에도 포함됩니다.
>
> **검증 한계**: 실제 로그인해서 매도 버튼을 눌러 KIS에 주문이 나가는 것까지는 확인하지 못했습니다 — 공유 모의계좌라 대신 눌러볼 계정이 없습니다. 기존 실주문 데이터(삼성전자 3주·NAVER 2주)로 새 집계 로직을 손으로 대조해 계좌 화면과 일치하는 것만 확인했습니다. 장중에 직접 사고→팔아보는 실측이 필요합니다.

### 4.2e 8/7 — 코스피 전 종목 확대 (Could Have를 원래 계획보다 크게 확대)

4.3절 원래 계획은 "종목 확대 100 → 200"(0.5h)이었습니다. 사용자가 "왜 검색이 코스피 상위 종목만 되냐"고 물어서(예: "금호에이치티" 검색 실패) 대조해보니, 그 자리에서 200이 아니라 **코스피 전체**로 가는 게 맞다고 판단했습니다.

- KIS가 배포하는 코스피 종목마스터 정적 파일(`kospi_code.mst.zip`, 인증 불필요)을 받아 파싱 — 그룹코드가 "ST"(주권)인 것만 걸러 코스피 전체 상장 상품 2,558개 중 **915종목**을 추출(ETF 1,160개·ETN 372개 등은 제외)
- `stocks` 테이블에 upsert — 기존 357종목은 유지, 558종목 신규 추가
- **검증 한계**: 915개 전부가 KIS 모의투자에서 실제로 시세·주문까지 매끄럽게 되는지는 전수 검증하지 못했습니다. 화면 자체에 실패 처리(`quoteError` 안내)가 이미 있어 최악의 경우 조용히 실패 안내만 뜨는 정도입니다.

### 4.2f 8/7 — DART 공시·뉴스 연동 (Won't Have 항목을 뒤집음, AI 해석 재료로만 한정)

사용자가 "DART·뉴스 데이터 연동해보자"고 요청했습니다. 4.4절이 "뉴스·공시 수집"을 뺀 이유(외부 데이터 범위가 큼)는 여전히 유효해서, **새 화면·탭을 만들지 않고 기존 AI-1(시세 해석)의 재료를 보강하는 데만 한정**했습니다. 🔄 **이 "재료로만 한정" 결정은 같은 날 저녁에 뒤집혔습니다 — 4.2g절 참고.**

| 기능 | 왜 추가했나 | 왜 Must는 아니었나 |
|---|---|---|
| DART 종목마스터로 종목코드 ↔ DART 고유번호 매핑(`stocks.dart_corp_code`) | 공시 조회는 회사 단위(고유번호) API라 종목코드로 바로 못 물어봄. 코스피 915종목 중 805개 매핑(누락 110개는 전부 우선주 — 공시는 회사 단위라 원래 개별 매핑이 없음) | 판단 근거 기록이라는 성공 기준과 직접 관련 없음 |
| 최근 공시 3건(`lib/dart.ts`) | 거래소공시(`pblntf_ty=I`)만 필터 — 필터 없이 받으면 임원 지분 신고 같은 일상적 신고가 대부분이라 재료로는 잡음이었음. 실적·배당·자사주 같은 실제 이벤트만 남김 | 위와 같음 |
| 최근 뉴스 헤드라인 3건(`lib/news.ts`) | 구글 뉴스 RSS 사용 — 키 발급 없이 종목명 검색만으로 됨 | 위와 같음 |

> 🔴 **"재료 보강"으로 범위를 좁힌 이유.** 공시·뉴스를 원문 그대로 화면에 목록으로 띄우는 건 이 프로젝트의 핵심(판단 근거를 직접 쓰게 하는 것)과 무관하게 화면·기능만 늘립니다. 대신 AI-1 프롬프트에 "있었던 일" 사실로만 넣고, 좋다/나쁘다 평가나 매수·매도 권유로 잇지 말라는 금지 규칙을 별도로 붙였습니다(`SAFETY_RULES`와 같은 원칙). 실측(삼성전자)으로 "7월 30일 자율공시가 있었다", "프리마켓에서 소폭 반등했다는 소식" 같은 사실 서술만 나오는 것을 확인했습니다.
>
> 🔄 **이 판단은 몇 시간 뒤 뒤집혔습니다.** "화면만 늘린다"는 논리에 빠진 반대편 문제를 못 봤습니다 — 4.2g절.
>
> **부작용**: `stocks`에 `dart_corp_code` 컬럼 추가. 새 환경변수 `DART_API_KEY` 필요(로컬·Vercel 등록 완료).

### 4.2g 8/7 저녁 — 공시뉴스 탭 추가 (4.2f의 "재료로만 한정"을 뒤집음)

사용자 지적: **"공시 데이터를 AI만 알게 하는 건 별로다. 사용자도 알 수 있게 종목정보 옆에 공시뉴스 탭을 만들어달라."**

**이 지적이 몇 시간 전 4.2f의 논리보다 강했습니다.** 4.2f는 "원문 목록은 화면만 늘린다"고 봤는데, 그 반대편에 더 큰 문제가 있었습니다 — 공시·뉴스를 **AI만 보고 사용자는 못 보면, AI가 요약한 "최근 소식" 줄을 사용자가 검증할 방법이 없습니다.** 이 프로젝트의 핵심 원칙은 "AI가 대신 판단해주지 않는다"인데, 원본을 감추면 사용자에게 남는 선택지는 AI 말을 믿는 것뿐이라 그 원칙과 정면으로 어긋납니다. 판단 근거를 직접 쓰게 하는 서비스라면 **그 근거의 재료도 직접 볼 수 있어야 합니다.**

| 기능 | 왜 추가했나 | 왜 Must는 아니었나 |
|---|---|---|
| `/api/disclosures` (`app/api/disclosures/route.ts`) | 기존엔 AI 해석 라우트(`/api/ai/explain`) 안에서만 공시·뉴스를 불렀음. 화면이 직접 쓰려면 별도 라우트가 필요 | 4.2f 시점엔 AI 재료로만 쓸 계획이었으므로 없어도 됐음 |
| 공시뉴스 탭 (`components/DisclosureNews.tsx`) | 공시·뉴스를 태그(`공시`/`뉴스`)로 구분해 제목·날짜만 나열. **해석·평가는 넣지 않음** | 화면 구성일 뿐, 이 탭 없이도 주문·근거 기록 흐름은 완결됨 |

> 🔴 **AI 해석과 겹치는 것은 의도한 것입니다.** 같은 재료가 AI-1의 "최근 소식" 줄(맥락 붙은 요약)과 이 탭(원문 목록) 양쪽에 나옵니다. 중복이 아니라 **대조 수단**입니다 — 4.2b절에서 "AI 해석이 언급하는 값은 표에도 있어야 한다"(`TradeFlow.tsx` 주석)고 정한 것과 같은 원칙이고, 그때는 PER·BPS에, 이번엔 공시·뉴스에 적용했습니다.
>
> **탭에서는 해석을 하지 않습니다.** 제목·날짜·출처 구분만 보여주고 요약·평가·정렬 가중치를 넣지 않았습니다. 여기서 "중요한 공시" 같은 걸 표시하기 시작하면 4.4절의 "종목 추천" 경계를 넘습니다.
>
> **부작용 없음**: 새 테이블·컬럼·환경변수 없이 기존 `dart_corp_code`·`DART_API_KEY`를 그대로 씁니다. 탭이 2개(차트·호가 / 종목정보)에서 3개(+공시뉴스)로 늘었습니다.
>
> **미흡한 점**: `/api/dividend`·`/api/financial-ratio`에는 있는 TTL 캐시를 `/api/disclosures`에는 붙이지 않았습니다. KIS가 아니라 DART·구글 뉴스라 EGW00201 레이트리밋과는 무관하지만, 탭을 열 때마다 외부 호출이 나갑니다. 4일 프로젝트의 트래픽에서는 문제가 없고, 실서비스로 가면 캐시가 필요합니다.

## 7. Scope Creep 방어

새 기능이 떠오르면 아래 3개를 전부 만족하지 않으면 `Could` 또는 `Won't`로 보냅니다.

```
1. 이 기능이 없으면 핵심 가정을 검증할 수 없는가?
2. 이 기능이 없으면 MVP 사용자 흐름이 끊기는가?
3. Must 합계가 22.3h를 넘지 않는가?
```

**4일 프로젝트에서 가장 흔한 실패는 기능 부족이 아니라 미완성입니다.**

### 이번에 특히 유혹적일 기능

| 유혹 | 왜 참아야 하는가 |
|---|---|
| 자연어 채팅창 | "AI 서비스답다"는 인상 때문에 끌립니다. 하지만 4h가 들고, 폼보다 정확도가 낮으며, **웹으로 옮긴 이유와 정반대**입니다 |
| 🔄 실시간 차트 | 화려하지만 판단 근거와 무관합니다. **Day 1 밤에 참지 못하고 만들었습니다** — 사용자가 직접 요청했고, 캔들·이동평균선은 빼고 종가 선만 남겨 "기술적 분석"이 아니라는 선은 지켰습니다(4.2b절). 유혹에 넘어간 사실 자체는 숨기지 않습니다 |
| 로그인 방식 확대 (이메일 가입, 프로필 편집 등) | Google OAuth 1개로 REQ-03·04를 충분히 만족합니다. 여러 로그인 수단을 두는 건 4일 범위 밖입니다 |
| 종목 추천 AI | 가장 그럴듯해 보이지만 유사투자자문 위험이고 목적과 반대 방향입니다 |
| 🔄 디자인 다듬기 | 끝이 없습니다. **Day 4 오후에만 손댑니다** — 원칙과 다르게 Day 1 밤에 화면 전체(폰트·헤더·레이아웃)를 다시 짰습니다. 다행히 주문 흐름(`/api/order`) 자체는 안 건드렸습니다. **Day 4에는 이 항목에 다시 손대지 않는 것으로 되돌립니다** |

> ⚠️ **이 절이 경고한 두 유혹에 실제로 넘어갔습니다.** 원칙을 몰라서가 아니라, 6.1/6.2(실주문)를 아직 안 끝낸 상태에서 다른 작업을 계속 받은 결과입니다. 다음 세션은 이 표를 먼저 보고, **6.1/6.2 전에는 새 유혹에 응하지 않는 것**을 원칙으로 삼습니다.
>
> **🔄 8/7: 6.1/6.2는 끝났지만 유혹은 안 끝났습니다.** 같은 날 배당·재무·탭 구조·지정가 주문·튜토리얼까지 이어서 들어갔습니다(4.2c절). 6.1/6.2가 끝나 데드라인 압박은 풀렸지만, 그 뒤로도 스코프 대조 없이 기능이 계속 늘어난 것은 이 표의 원칙이 "데드라인 전"에만 적용되는 것처럼 읽혔기 때문일 수 있습니다. **다음에는 6.1/6.2 여부와 무관하게, 새 기능 요청이 오면 항상 이 표부터 대조합니다.**
>
> **🔄 8/7 저녁: 위 원칙을 바로 다음 요청에서 안 지켰습니다.** 공시뉴스 탭(4.2g절)을 만들 때 이 문서를 먼저 열지 않고 바로 코드부터 짰습니다. 매도(4.2d)·DART 연동(4.2f) 때는 대조가 작동했는데 이번엔 건너뛰었습니다.
>
> **결과적으로 기능 자체는 옳았습니다** — 사용자 지적("AI만 알게 하는 건 별로다")이 4.2f의 논리보다 강했고, 대조를 했더라도 결론은 "4.2f가 틀렸으니 뒤집는다"였을 것입니다. **하지만 대조를 건너뛴 비용은 따로 있었습니다:** 4.2f절이 "새 화면·탭을 만들지 않는다"고 명시하고 있다는 걸 그 자리에서 못 봤고, 그래서 문서가 코드와 몇 시간 동안 정면으로 모순된 채 남아 있었습니다. **대조의 값어치는 기능을 막는 데 있는 게 아니라, 뒤집는 순간 무엇이 뒤집히는지 알게 해주는 데 있습니다.**
