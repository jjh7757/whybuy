### 🔴 왜 화면보다 `lib/kis.ts`를 먼저 만듭니까?

**Vercel에서 KIS를 호출할 수 있는지가 이 프로젝트의 유일한 미확인 가정이기 때문입니다.**

```
확인됨:  KIS API 자체는 동작한다        (프로젝트 2에서 n8n으로 확인)
미확인:  고정 IP 없는 Vercel에서도 되는가  ← 오늘 확인
```

여기서 막히면 **화면을 아무리 잘 만들어도 소용이 없습니다.** 화면은 하루면 만들지만, 주제를 바꾸는 결정은 늦을수록 손해가 커집니다.

**Day 1 종료 확인**
- [ ] 🔴 **Vercel 배포 URL을 열면 내 모의계좌 예수금이 표시됩니다.**
- [ ] `kis_tokens`에 행이 1개 있고 `expires_at`이 미래입니다.
- [ ] 🔴 **`expires_at`을 강제로 과거로 바꾼 뒤 새로고침하면 재발급되고 화면이 정상입니다.**
- [ ] 새로고침을 5번 해도 `kis_tokens`의 토큰이 바뀌지 않습니다. (캐시가 동작함)
- [ ] `NEXT_PUBLIC_`이 붙은 환경변수가 2개뿐입니다.
- [ ] Supabase에 테이블 6개가 있습니다.

> ⚠️ **오늘 안 되면 오늘 밤에 판단하지 않습니다.** 내일 12:00까지 시도하고 그때 결정합니다. 밤에 내리는 판단은 대체로 과합니다.

| 11 | Scope creep (채팅창 유혹) | 미완성 발표 | **Day 4 신규 개발 금지.** Should는 Day 3 종료 후 버퍼가 남을 때만 |
| 12 | 시크릿 창에서 실패 | REQ-04 미달 | Day 4 6.5를 문서보다 앞에 배치 |
| 13 | 표본 부족으로 측정값 과장 | 발표 신뢰도 하락 | **비율이 아니라 실수로 말함** (`6건 중 6건`) |
| 14 | 계좌번호 노출 | 보안 사고 | 녹화 후 재생 확인. `.gitignore` 점검 |

### 가장 위험한 3개

**1위 — Vercel × KIS 연결 (위험 1).** 유일한 미확인 가정이고, 실패하면 시간을 더 써도 해결되지 않습니다. 그래서 Day 1의 첫 작업이고, **판단 시점(8/7 12:00)과 대안을 미리 정해 두었습니다.**

**2위 — 거래일이 이틀뿐 (위험 2).** 시간을 더 써서 해결할 수 없는 제약입니다. 오늘과 내일 안에 주문 검증과 녹화를 끝내야 합니다.

**3위 — 토큰 만료 경로 (위험 3).** 24시간 내 개발로는 절대 드러나지 않고, **발표일 월요일 아침에 처음 터집니다.** 만료시각을 강제로 바꿔보지 않으면 발견할 방법이 없습니다.

## 6. 버퍼

| 구간 | 여유 | 용도 |
|---|---:|---|
| Day 2 | 0.2h | 주문 검증 재시도 |
| Day 3 | 0.3h | AI 프롬프트 조정 |
| Day 4 | — | 리허설 후 남는 시간 전부 |
| 기능 버퍼 | 3.5h | Should 4개를 전부 포기하면 확보되는 시간 |

### 버퍼 사용 우선순위

```
1순위  Day 2 주문 검증·녹화 (실패하면 발표에서 주문을 못 보여줌)
2순위  Day 1 KIS 연결 (실패하면 주제가 바뀜)
3순위  Day 4 시크릿 창 검수에서 발견한 문제
4순위  예외 UI 보완 (REQ-05)
5순위  발표자료 보완
6순위  Should 1순위 (AI-3 용어 설명)
```

**6순위는 1~5순위가 전부 끝난 뒤에만 시작합니다.** Day 4 오전까지 완성되지 않으면 되돌립니다.

## 7. 각 날짜의 통과 조건

| Day | 넘어가도 되는 조건 |
|---|---|
| Day 1 목 | 🔴 **배포 URL에서 예수금이 보인다 + 토큰 재발급 경로가 확인됐다** |
