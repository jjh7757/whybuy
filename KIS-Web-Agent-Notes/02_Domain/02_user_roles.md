# 사용자 역할

- 작성일: 2026-08-06 (개정: 가상 예산 모델로 전환)

---

## 1. 이번 프로젝트에서 역할 설계가 필요해진 이유

프로젝트 2에서는 사용자가 1명이었고 `chat_id` 화이트리스트로 나머지를 전부 막았습니다.

프로젝트 3은 다릅니다. **REQ-04가 공개 URL을 요구합니다.** 그런데 이 서비스는 **KIS 모의계좌 1개에 실제로 주문을 넣습니다.**

```
공개해야 한다는 요구  ↔  계좌 하나를 보호해야 한다는 요구
```

### 🔴 정식 서비스라면 이렇게 풉니다

```
KIS 모의계좌를 N개 미리 개설한다
→ 방문자마다 계좌를 하나씩 배정한다
→ 각자 자기 계좌에서 자유롭게 주문한다
```

**이번 4일 MVP에는 계좌가 1개뿐입니다.** 그래서 실제 계좌를 나누는 대신, **우리 DB 안에 가상의 예산 한도를 만들어 계좌 하나를 여러 방문자가 나눠 쓰게** 합니다.

```
정식 서비스:  계좌 A → 방문자 A,  계좌 B → 방문자 B, ...  (물리적으로 분리)
이번 MVP:    계좌 1개 → 방문자 A는 500만원까지, 방문자 B는 500만원까지, ...  (가상으로 분리)
```

**주문 자체는 진짜 KIS 모의계좌에서 실행됩니다.** 가상 예산은 "이 방문자가 이 계좌에서 얼마까지 쓸 수 있는가"를 우리가 관리하는 것이지, 별도 계좌를 만드는 것이 아닙니다.

---

## 2. 역할 — 이제 1개입니다 (방문자만 있습니다)

이전 설계의 **소유자/방문자 2단계 권한**을 없앴습니다. 모두가 같은 권한으로 주문할 수 있고, 다만 **각자 쓸 수 있는 금액에 한도**가 있을 뿐입니다.

| 할 수 있는 것 | 조건 |
|---|---|
| 화면 3개 전부 열람 | 누구나 (로그인 불필요) |
| 종목 검색·시세 조회 (AI 해석 포함) | 누구나 (로그인 불필요) |
| **매수 주문 실행** | 🔴 **Google 로그인 + 가상 예산 한도 안에서만** |
| 회고 화면 열람 | 로그인 시 **자기 주문만** (다른 사용자 것은 안 보임) |

### 왜 패스코드를 없앴습니까?

패스코드는 "계좌를 지키기 위해 실행 자체를 막는" 접근이었습니다. **가상 예산은 계좌를 지키면서도 실행을 막지 않는 접근입니다.** 방문자가 실제로 주문을 넣어볼 수 있어야 REQ-04("바로 쓸 수 있어야 한다")의 의미가 완전해지고, 시연 상대도 직접 눌러볼 수 있습니다.

## 3. 사용자 식별 — Google 로그인 (Supabase Auth)

**지속 가능한 서비스를 목표로 하므로 익명 쿠키가 아니라 실제 계정을 씁니다.** 쿠키는 브라우저를 지우거나 기기를 바꾸면 끊기지만, 로그인 계정은 기기를 넘나들며 유지됩니다. 예산도, 회고 기록도 "내 계정"에 계속 쌓입니다.

```
1. 첫 방문 시 "Google로 계속하기" 버튼만 보입니다.
2. Supabase Auth의 Google OAuth로 로그인합니다. (비밀번호 없음)
3. 콜백에서 세션이 생성되고, user_id(auth.users.id, UUID)가 확정됩니다.
4. 첫 주문 시도 시 user_wallets에 없으면 행을 만들고 기본 예산을 지급합니다.
```

| 방식 | 개발 시간 | 이 프로젝트에 맞는가 |
|---|---:|---|
| 익명 쿠키 | 0.3h | ❌ 기기·브라우저를 바꾸면 예산·기록이 끊깁니다. 지속 가능한 서비스와 맞지 않습니다 |
| Supabase Auth 이메일+비밀번호 | 2h | ⚠️ 가입 화면이 따로 필요하고, 비밀번호 찾기 흐름이 4일 안에 굳이 필요한가 하는 문제가 남습니다 |
| **Supabase Auth Google OAuth (채택)** | 2h | ✅ 버튼 한 번으로 끝. 이메일 대기 없이 발표 시연에 안전하고, 기기를 넘나드는 지속성이 생깁니다 |

### Google Cloud 설정이 선행 작업입니다

Google OAuth를 쓰려면 Google Cloud Console에 **OAuth 동의 화면**을 한 번 만들어야 합니다. 테스트 사용자 100명까지는 별도 심사 없이 바로 쓸 수 있어, 4일 프로젝트 규모에는 지장이 없습니다. Supabase 대시보드의 Authentication → Providers에서 클라이언트 ID·시크릿을 등록하면 끝입니다.

> ⚠️ Google 계정이 없는 방문자는 로그인할 수 없습니다. **이것은 결함이 아니라 알려진 한계**로 문서화합니다. 4일 MVP 범위에서는 Google 계정 보급률을 감안하면 실질적 장벽이 낮다고 판단합니다.

## 4. 가상 예산 (`user_wallets`)

```sql
create table user_wallets (
  user_id          uuid primary key references auth.users(id),
  allocated_amount integer not null default 5000000,
  created_at       timestamptz not null default now()
);
```

| 항목 | 값 | 근거 |
|---|---|---|
| 기본 할당액 | 500만원 | 코스피 주요 종목 몇 주를 사보기에 충분하고, 계좌 전체를 위협하지 않는 크기 |
| 재충전 | 없음 | 4일 프로젝트에 필요 없습니다. 소진되면 "가상 예산을 모두 사용했습니다"로 안내 |
| 조정 | Supabase 대시보드에서 특정 `user_id`의 값을 직접 수정 (앱 기능 아님) | 개발자가 테스트 중 자기 한도를 늘리고 싶을 때 씀 |

### 🔴 가상 예산과 실제 계좌 예수금은 서로 다른 검사입니다

| 검사 | 지키는 대상 | 위치 |
|---|---|---|
| 실제 계좌 예수금 확인 (기존 예외 2.5) | **계좌 전체** | 모든 방문자 합산 사용 후에도 남아 있어야 함 |
| 가상 예산 확인 (신규 예외 2.11) | **방문자 개인** | 한 명이 계좌를 몰아 쓰는 것을 막음 |

**가상 예산이 1차 방어선이고, 실제 예수금 확인이 최종 방어선입니다.** 가상 예산이 잘못 설계되어도 계좌 자체는 예수금 확인에서 다시 걸립니다.

## 5. 방문자에게 무엇을 보여주는가 (REQ-05)

| 위치 | 내용 |
|---|---|
| 첫 화면 상단 | "이 서비스는 **왜 샀는지**를 반드시 적게 하는 모의투자 도구입니다. Google로 로그인하면 500만원의 모의 투자금이 주어집니다." |
| 주문 폼 | 남은 예산이 실시간으로 표시됩니다 ("남은 예산 4,318,000원") |
| 확인 모달 | "이 주문 후 남는 예산: OOO원" |
| 예산 초과 시 | "가상 예산을 초과했습니다. 남은 한도 OOO원. 수량을 줄여보세요." (예외 2.11) |
| 회고 화면 | 자기 주문·근거만 보임. 데이터가 없으면 "아직 기록이 없습니다 + [첫 주문 해보기]" |

## 6. AI 호출 남용 대응 (기존 유지)

방문자가 AI 해석을 무제한으로 누르면 Gemini 사용량이 소진됩니다.

| 대응 | 방식 |
|---|---|
| 결과 캐시 | 같은 종목의 시세 해석은 5분간 재사용 |
| 화면당 호출 제한 | 자동 호출 금지. 버튼을 눌러야 호출 |
| 실패 시 원본 노출 | AI가 실패해도 원본 수치는 표시 |

> 가상 예산은 **주문(KIS 호출)**을 제한하고, 캐시·수동 호출은 **AI(Gemini 호출)**를 제한합니다. 두 남용 경로를 각각 다른 방법으로 막습니다.

## 7. 이 설계의 한계 (정직하게 문서화)

| 한계 | 이유 | 정식 서비스라면 |
|---|---|---|
| Google 계정이 없으면 이용(주문)이 불가함 | OAuth 제공자를 1개만 붙임 | 이메일 로그인 등 다른 제공자 추가 |
| 여러 사용자가 동시에 계좌 예수금을 나눠 씀 | 계좌가 1개 | 계좌를 물리적으로 분리 |
| 사용자별 동시 주문 경쟁 조건 미대응 | 4일 범위 밖 | 분산 락 또는 트랜잭션 격리 강화 |
