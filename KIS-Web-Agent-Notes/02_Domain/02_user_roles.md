- **갱신일: 2026-08-07** — 열람 권한(2절)·로그인 화면(3절)·재충전 원칙(4절)·AI 남용 대응(6절)을 실제 구현에 맞췄습니다

## 1. 이번 프로젝트에서 역할 설계가 필요해진 이유

프로젝트 2에서는 사용자가 1명이었고 `chat_id` 화이트리스트로 나머지를 전부 막았습니다.

프로젝트 3은 다릅니다. **REQ-04가 공개 URL을 요구합니다.** 그런데 이 서비스는 **KIS 모의계좌 1개에 실제로 주문을 넣습니다.**

```
공개해야 한다는 요구  ↔  계좌 하나를 보호해야 한다는 요구
```

### 🔴 정식 서비스라면 이렇게 풉니다

```
KIS 모의계좌를 N개 미리 개설한다
→ 방문자마다 계좌를 하나씩 배정한다
→ 각자 자기 계좌에서 자유롭게 주문한다
```

**이번 4일 MVP에는 계좌가 1개뿐입니다.** 그래서 실제 계좌를 나누는 대신, **우리 DB 안에 가상의 예산 한도를 만들어 계좌 하나를 여러 방문자가 나눠 쓰게** 합니다.

```
정식 서비스:  계좌 A → 방문자 A,  계좌 B → 방문자 B, ...  (물리적으로 분리)
이번 MVP:    계좌 1개 → 방문자 A는 500만원까지, 방문자 B는 500만원까지, ...  (가상으로 분리)
```

**주문 자체는 진짜 KIS 모의계좌에서 실행됩니다.** 가상 예산은 "이 방문자가 이 계좌에서 얼마까지 쓸 수 있는가"를 우리가 관리하는 것이지, 별도 계좌를 만드는 것이 아닙니다.

## 2. 역할 — 이제 1개입니다 (방문자만 있습니다)

이전 설계의 **소유자/방문자 2단계 권한**을 없앴습니다. 모두가 같은 권한으로 주문할 수 있고, 다만 **각자 쓸 수 있는 금액에 한도**가 있을 뿐입니다.

| 할 수 있는 것 | 조건 |
|---|---|
| ~~화면 3개 전부 열람~~ 🔄 **`/trade` 전체 열람** | 누구나 (로그인 불필요) |
| 종목 검색·시세·차트·재무·배당·공시뉴스 (AI 해석 포함) | 누구나 (로그인 불필요) |
| 🔄 **`/`(내 계좌)·`/journal`(지난 근거) 내용 열람** | 🔴 **로그인 필요** — 미로그인 시 안내 문구만 보입니다 |
| ~~**매수 주문 실행**~~ 🔄 **매수 주문 실행** | 🔴 **Google 로그인 + 가상 예산 한도 안에서만** |
| 🆕 **매도 주문 실행** | 🔴 Google 로그인 + **가상 예산이 아니라 보유 수량이 한도** (`availableToSell`) |
| 회고 화면 열람 | 로그인 시 **자기 주문만** (다른 사용자 것은 안 보임) |

> 🔄 **"화면 3개 전부 로그인 없이 열람"은 틀린 서술이 됐습니다.** URL 자체는 누구나 열리지만 안에 내용이 없습니다 — `/`는 `"로그인하면 내 예산과 주문이 여기에 표시됩니다"`만(`components/AccountCard.tsx`), `/journal`은 `"내 근거를 보려면 로그인이 필요합니다"`만 나옵니다(`app/journal/page.tsx`). **로그인 없이 내용이 온전히 보이는 화면은 `/trade` 하나입니다.**
>
> **설계가 바뀐 게 아니라 계획이 처음부터 앞뒤가 안 맞았습니다.** 같은 표가 아래 줄에서 "회고 화면은 로그인 시 자기 주문만"이라고 이미 적어놓고, 위 줄에서 "3개 전부 로그인 불필요"라고 적었습니다. 익명 쿠키 방식이었다면 성립했을 서술이 Google 로그인(3절)으로 바뀌면서 함께 갱신되지 않은 것입니다.
>
> 🔴 **REQ-04("링크를 받은 사람이 아무 설치 없이 바로 쓸 수 있어야 한다")는 여전히 만족합니다.** 처음 온 사람이 가입 없이 볼 수 있는 것이 `/trade`이고, 종목 검색·시세·차트·재무·배당·공시·AI 해석이 전부 여기 있습니다. **로그인이 필요해지는 시점은 "자기 데이터가 생긴 다음"**입니다. 다만 첫 화면(`/`)이 로그인 안내부터 보여준다는 점은 인정해야 할 마찰입니다 — 처음 온 사람은 `/`에 먼저 도착합니다.
>
> 🆕 **매도의 한도는 예산이 아닙니다.** 매수는 "가상 예산 → 실제 예수금" 2단 검증을 거치지만, 매도는 **"이 서비스로 실제 보유한 수량"**만 봅니다(`app/api/order/route.ts`). 파는 데는 현금이 필요 없고, 실제 보유 부족은 KIS가 거부하면 그대로 전달됩니다. **검증 경로가 매수와 완전히 갈라진 것**이고, 이것은 [[../07_Submit/02_scope_reduction\|범위 축소 설명서]] 6절에 새 한계로 적어뒀습니다.

### 왜 패스코드를 없앴습니까?

패스코드는 "계좌를 지키기 위해 실행 자체를 막는" 접근이었습니다. **가상 예산은 계좌를 지키면서도 실행을 막지 않는 접근입니다.** 방문자가 실제로 주문을 넣어볼 수 있어야 REQ-04("바로 쓸 수 있어야 한다")의 의미가 완전해지고, 시연 상대도 직접 눌러볼 수 있습니다.

## 3. 사용자 식별 — Google 로그인 (Supabase Auth)

**지속 가능한 서비스를 목표로 하므로 익명 쿠키가 아니라 실제 계정을 씁니다.** 쿠키는 브라우저를 지우거나 기기를 바꾸면 끊기지만, 로그인 계정은 기기를 넘나들며 유지됩니다. 예산도, 회고 기록도 "내 계정"에 계속 쌓입니다.

```
1. ~~첫 방문 시 "Google로 계속하기" 버튼만 보입니다.~~
   🔄 머리말 오른쪽 위에 [로그인] 버튼이 항상 있습니다. 로그인 전에도 화면은 그대로 보입니다.
2. 버튼을 누르면 Supabase Auth의 Google OAuth로 넘어갑니다. (비밀번호 없음)
3. 콜백(/auth/callback)에서 세션이 생성되고, user_id(auth.users.id, UUID)가 확정됩니다.
   🆕 실패하면 /auth/error로 보냅니다.
4. 🆕 로그인 전에 채우던 주문 초안(종목·수량·근거·지정가)이 있으면 복원합니다.
5. 첫 주문 시도 시 user_wallets에 없으면 행을 만들고 기본 예산을 지급합니다.
```

> 🔄 **"버튼만 보이는 화면"은 만들지 않았습니다.** 로그인 전용 랜딩을 따로 두면 처음 온 사람이 **무엇을 주는 서비스인지 보기도 전에 로그인부터 요구받습니다.** 대신 머리말에 [로그인] 버튼을 상시로 두고, 로그인이 필요한 자리마다 `"오른쪽 위의 [로그인] 버튼을 눌러주세요"`로 안내합니다(`components/AuthButton.tsx`·`AccountCard.tsx`·`app/journal/page.tsx`). **라벨도 "Google로 계속하기"가 아니라 "로그인" 한 단어**입니다.
>
> 🆕 **4번(초안 복원)은 계획에 없던 항목입니다.** 주문 폼을 다 채운 뒤에야 "로그인이 필요합니다"를 만나면, 로그인하고 돌아왔을 때 빈 폼이 기다립니다. 채우던 값을 `sessionStorage`에 두었다가 콜백 뒤에 되살립니다(`components/TradeFlow.tsx`). **로그인을 나중으로 미룬 설계가 만들어낸 비용**입니다.
>
> ⚠️ **로그인 수단이 Google 하나뿐이라는 사실이 버튼에 드러나지 않습니다.** 라벨이 "로그인"이라 눌러야 Google 화면이 뜹니다. 7절의 한계(Google 계정이 없으면 주문 불가)와 이어지는 문제입니다.

| 방식 | 개발 시간 | 이 프로젝트에 맞는가 |
|---|---:|---|
| 익명 쿠키 | 0.3h | ❌ 기기·브라우저를 바꾸면 예산·기록이 끊깁니다. 지속 가능한 서비스와 맞지 않습니다 |
| Supabase Auth 이메일+비밀번호 | 2h | ⚠️ 가입 화면이 따로 필요하고, 비밀번호 찾기 흐름이 4일 안에 굳이 필요한가 하는 문제가 남습니다 |
| **Supabase Auth Google OAuth (채택)** | 2h | ✅ 버튼 한 번으로 끝. 이메일 대기 없이 발표 시연에 안전하고, 기기를 넘나드는 지속성이 생깁니다 |

### Google Cloud 설정이 선행 작업입니다

Google OAuth를 쓰려면 Google Cloud Console에 **OAuth 동의 화면**을 한 번 만들어야 합니다. 테스트 사용자 100명까지는 별도 심사 없이 바로 쓸 수 있어, 4일 프로젝트 규모에는 지장이 없습니다. Supabase 대시보드의 Authentication → Providers에서 클라이언트 ID·시크릿을 등록하면 끝입니다.

> ⚠️ Google 계정이 없는 방문자는 로그인할 수 없습니다. **이것은 결함이 아니라 알려진 한계**로 문서화합니다. 4일 MVP 범위에서는 Google 계정 보급률을 감안하면 실질적 장벽이 낮다고 판단합니다.

## 4. 가상 예산 (`user_wallets`)

```sql
create table user_wallets (
  user_id          uuid primary key references auth.users(id),
  allocated_amount integer not null default 5000000,
  created_at       timestamptz not null default now()
);
```

| 항목 | 값 | 근거 |
|---|---|---|
| 기본 할당액 | 500만원 | 코스피 주요 종목 몇 주를 사보기에 충분하고, 계좌 전체를 위협하지 않는 크기 |
| 재충전 | ~~없음~~ 🔄 **재충전 기능은 없지만, 매도가 체결되면 예산이 되돌아옵니다** | 아래 참고 |
| 소진 시 안내 | ~~"가상 예산을 모두 사용했습니다"~~ 🔄 **"가상 예산을 초과했습니다. 남은 한도 OOO원. 수량을 줄여보세요."** | 남은 한도를 같이 알려줘야 사용자가 **몇 주로 줄일지** 판단할 수 있습니다 (`app/api/order/route.ts`) |
| 조정 | Supabase 대시보드에서 특정 `user_id`의 값을 직접 수정 (앱 기능 아님) | 개발자가 테스트 중 자기 한도를 늘리고 싶을 때 씀 |

### 🔴 "재충전 없음" 원칙이 어떻게 바뀌었는가

**원래 뜻은 "예산을 다 쓴 사용자에게 돈을 더 주지 않는다"였고, 그 뜻은 지금도 지켜집니다.** `allocated_amount`를 올려주는 앱 기능은 없습니다.

바뀐 것은 **"쓴 돈"의 정의**입니다. 계획 시점의 소진액은 `Σ 매수 금액`이었고 단조 증가하는 값이었습니다. 매도가 들어오면서 `lib/portfolio.ts`의 `lockedAmount()`가 세 갈래로 다시 쓰였고, **매도 체결분은 음수로 계산됩니다.**

```
매수 체결분        + filled_qty × filled_price     (실제로 나간 돈)
매수 대기중 잔량    + (qty - filled_qty) × limit_price  (묶어둔 돈)
매도 체결분        - filled_qty × filled_price     ← 🔴 예산으로 돌아옵니다
매도 대기중 잔량      0                              (아직 현금이 안 들어옴)
```

**결과적으로 사실상의 재충전 경로가 생겼습니다. 이것은 실수가 아니라 의도한 설계입니다.**

1. 실제 증권 계좌가 그렇게 동작합니다. 팔면 현금이 돌아옵니다.
2. 팔아도 예산이 안 돌아오면 사용자는 한 번 산 종목을 **영원히 들고 있어야** 합니다. 그러면 매도 근거를 기록해볼 기회 자체가 사라져 **이 프로젝트의 성공 기준과 정면으로 어긋납니다.**

> ⚠️ **부작용은 인정합니다.** 예산이 사실상 무한히 회전할 수 있고, 사고팔기를 반복하면 **누적 거래액에는 한도가 없습니다.**
>
> 다만 한도가 지키려던 것은 "한 사람이 **계좌 예수금을 소진시키는 것**"이고, 매도하면 계좌 예수금도 함께 돌아오므로 **그 위험 자체가 커지지는 않습니다.** 막지 못하는 것은 다른 형태의 몰아 쓰기(주문 건수·KIS 호출 횟수)이고, 그건 6절에서 따로 다룹니다.
>
> **문서에 "재충전 없음"만 적혀 있으면 발표에서 잘못 말하게 됩니다.** 정확히는 **"충전은 없지만 회수는 있다"**입니다.

### 🔴 가상 예산과 실제 계좌 예수금은 서로 다른 검사입니다

| 검사 | 지키는 대상 | 위치 |
|---|---|---|
| 실제 계좌 예수금 확인 (기존 예외 2.5) | **계좌 전체** | 모든 방문자 합산 사용 후에도 남아 있어야 함 |
| 가상 예산 확인 (신규 예외 2.11) | **방문자 개인** | 한 명이 계좌를 몰아 쓰는 것을 막음 |

**가상 예산이 1차 방어선이고, 실제 예수금 확인이 최종 방어선입니다.** 가상 예산이 잘못 설계되어도 계좌 자체는 예수금 확인에서 다시 걸립니다.

## 5. 방문자에게 무엇을 보여주는가 (REQ-05)

| 위치 | 내용 |
|---|---|
| 첫 화면 상단 | "이 서비스는 **왜 샀는지**를 반드시 적게 하는 모의투자 도구입니다. Google로 로그인하면 500만원의 모의 투자금이 주어집니다." |

## 6. AI 호출 남용 대응 (기존 유지)

방문자가 AI 해석을 무제한으로 누르면 Gemini 사용량이 소진됩니다.

| 대응 | 방식 |
|---|---|
| ~~결과 캐시~~ 🔄 | ~~같은 종목의 시세 해석은 5분간 재사용~~ ⚠️ **미구현.** [[../05_Scope/01_mvp_scope\|MVP 범위]] 4.2절에 Should Have(0.5h)로 남아 있습니다 |
| 화면당 호출 제한 | 자동 호출 금지. 버튼을 눌러야 호출 — ✅ 구현됨 |
| 실패 시 원본 노출 | AI가 실패해도 원본 수치는 표시 — ✅ 구현됨 |

> 🔄 **AI 결과 캐시는 만들지 않았습니다.** 캐시가 붙은 곳은 AI가 아니라 **외부 데이터 라우트 4곳**입니다 — `/api/chart`(60초, 분봉 180초) · `/api/dividend`(1시간) · `/api/financial-ratio`(1시간) · `/api/popular`(15초).
>
> **여기에 먼저 붙은 이유는 남용 방어가 아니라 레이트리밋(`EGW00201`)이었습니다.** 캐시를 만든 동기 자체가 이 절이 걱정하던 것과 달랐고, Gemini 쪽은 "버튼을 눌러야 호출"만으로 4일 트래픽에서 문제가 안 생겨 우선순위에서 계속 밀렸습니다. **막지 못한 경로는 그대로 남아 있습니다** — 같은 종목의 [AI 해석] 버튼을 반복해서 누르면 누를 때마다 Gemini를 호출합니다.
>
> ⚠️ **`/api/disclosures`에는 캐시가 없습니다**(4.2g절에 미흡한 점으로 기록됨). 탭을 열 때마다 DART·구글 뉴스에 요청이 나갑니다.
>
> ⚠️ **이 캐시들은 라우트 모듈 메모리(`Map`)에 있습니다.** 서버리스에서는 인스턴스마다 따로 존재하고 인스턴스가 죽으면 사라집니다. 4일 규모에서는 충분하지만 **"5분간 전역 재사용" 같은 보장은 아닙니다.**

> ~~가상 예산은 **주문(KIS 호출)**을 제한하고, 캐시·수동 호출은 **AI(Gemini 호출)**를 제한합니다.~~
>
> 🔄 **두 남용 경로를 각각 다른 방법으로 막는다는 구도는 맞았지만, 가상 예산이 KIS 호출을 다 막지는 못합니다.** 지정가 주문이 들어오면서 **예산 검증을 통과한 뒤에도** 사용자가 [체결 확인]·[취소]를 누를 때마다 KIS 호출이 추가로 나갑니다(`/api/order/[id]/check-fill`, `/api/order/[id]/cancel`). 시세·차트·배당·재무 조회는 애초에 로그인도 예산도 거치지 않습니다.
>
> **정확히는 이렇습니다: 예산은 주문 금액을 막고, 호출 횟수는 막지 못합니다.** 호출 횟수 쪽은 `lib/kis.ts`의 전역 큐(초당 1건)가 감당하고 있는데, **그건 남용 방어로 만든 것이 아니라 KIS 레이트리밋 대응으로 만든 것**입니다. 우연히 같은 자리를 지키고 있을 뿐이고, 악의적 반복 호출을 막는 장치는 이 서비스에 없습니다.

## 7. 이 설계의 한계 (정직하게 문서화)

| 한계 | 이유 | 정식 서비스라면 |
|---|---|---|
| Google 계정이 없으면 이용(주문)이 불가함 | OAuth 제공자를 1개만 붙임 | 이메일 로그인 등 다른 제공자 추가 |
| 여러 사용자가 동시에 계좌 예수금을 나눠 씀 | 계좌가 1개 | 계좌를 물리적으로 분리 |

| 🆕 **AI(Gemini) 호출에 캐시·횟수 제한이 없음** | Should Have로 두고 끝까지 안 만듦 (6절) | 사용자·종목 단위 rate limit + 결과 캐시 |

| 🆕 **매도 실주문을 끝까지 눌러 검증하지 못함** | 공유 모의계좌라 대신 눌러볼 계정이 없음 | 사용자별 계좌 배정 후 재현 테스트 |
