
### 흐름 B. 계좌 상황 확인 — `/`

> 🔄 **2026-08-06 변경.** 공용 KIS 모의계좌 잔고 전체를 보여주는 설계에서, **로그인 사용자가 이 서비스로 주문한 종목 + 남은 가상 예산**만 보여주는 설계로 바뀌었습니다. 모의계좌 1개를 여러 방문자가 공유하는 구조라, 전체 잔고를 그대로 보여주면 다른 방문자의 주문과 서비스 이전부터 있던 보유 종목이 "내 것"으로 보이는 문제가 있었습니다. (`lib/portfolio.ts`, `app/api/account/route.ts`)

```
0. 🔴 로그인하지 않았다면 계좌 정보를 조회하지 않고 로그인 안내(빈 상태)를 보여줍니다.
1. 사용자가 [내 계좌 보기]를 누릅니다.
2. 서버가 로그인 세션에서 user_id를 확인합니다.
3. 서버가 orders(이 서비스로 이 사용자가 넣은 주문)를 합산해 보유 종목과
   남은 가상 예산(지급액·사용액·잔액)을 계산합니다. (거부된 주문은 제외, 지갑 미생성 시 기본 500만원)
   → KIS 잔고조회를 직접 쓰지 않습니다. 시세만 KIS에서 보유 종목분만 조회합니다.
4. 남은 가상 예산과 보유 종목(주문가·현재가·평가손익)을 화면에 표로 표시합니다.
   🔴 시세 조회가 일부 실패해도 보유 목록과 예산은 그대로 표시되고, 실패한 종목만 `—`로 나갑니다.
5. 주문이 0건이면 "아직 주문한 종목이 없습니다" 빈 상태를 표시합니다.
6. 사용자가 [이게 무슨 뜻인가요?] 버튼을 누릅니다.
7. 서버가 Gemini에 숫자를 넘겨 초보자 언어 해석을 생성합니다.   ← AI-1
8. 해석 문장을 표 아래에 표시합니다.
9. account_diagnosed 이벤트를 기록합니다. (payload의 `deposit`은 실제 계좌 예수금이 아니라 **남은 가상 예산**입니다 — [[../03_Data_Event/03_event_catalog|이벤트 카탈로그]] 참고)
```

**7번이 이 화면의 가치입니다.** 숫자를 보여주는 것은 증권사 앱이 더 잘합니다. `평가손익 -32,000원 / -4.2%`를 "이것이 무슨 뜻이고 지금 무엇을 봐야 하는지"로 바꾸는 것이 차이입니다.

> ⚠️ 6번을 **버튼으로 둔 이유**: 화면 진입 시 자동 호출하면 새로고침마다 Gemini가 호출됩니다. ([[02_user_roles|사용자 역할]] 6절)

### 흐름 C. 종목 조회 — `/trade`

```
0. 🆕 화면에 들어오면 먼저 실시간 인기 종목이 순위로 보입니다. (KIS가 주는 최대치인 30건 중 지원 종목만, 보통 29건)
   여기서 바로 고르면 2번을 건너뛰고 4번으로 갑니다. (검색은 이름을 아는 사람용 길입니다)
1. 사용자가 검색창에 "삼성전자"를 입력합니다.
2. 서버가 stocks 테이블을 stock_name으로 조회합니다.
3-a. 결과가 1건이면 그 종목으로 진행합니다.
3-b. 결과가 2건 이상이면 후보 목록을 보여주고 사용자가 고릅니다.   ← 예외 2.2
3-c. 결과가 0건이면 안내합니다.                                  ← 예외 2.3
4. 서버가 KIS 시세조회를 호출합니다. 이어서 종가 그래프용 봉(기본은 일봉·최근 3개월)을 별도로 받아 옵니다.
5. 현재가·등락률·거래량과 정량지표(PER·PBR·EPS·BPS)를 표시합니다.
   🆕 종가 선그래프, `오늘 범위`·`52주 범위` 막대를 함께 보여줍니다.
   그래프는 일·주·월·년 4개 구간을 토글할 수 있습니다. 구간을 바꾸면 5번을 그 구간으로 다시 합니다.
   화면은 2단입니다 — 왼쪽 "이 종목이 어떤 상태인가", 오른쪽 "얼마나, 왜 살 것인가".
   🔴 KIS가 지표를 주지 않는 종목(우선주 등)은 `—`로 표시합니다. 0을 그대로 쓰면 "PER 0배"라는 없는 사실이 됩니다.
   적자 기업의 PER은 음수로 옵니다. 증권사 앱들처럼 값을 가리지 않고 그대로 표시하되, 해석은 AI가 맡습니다(아래).
6. 사용자가 [이 숫자 해석해줘]를 누르면 Gemini가 해석합니다.       ← AI-1
7. quote_retrieved 이벤트를 기록합니다.
```

> 🆕 **왜 검색이 아니라 목록이 첫 화면입니까?** 원래 설계는 검색창 하나로 시작했습니다. 그런데 그러면 **종목명을 이미 아는 사람만** 쓸 수 있습니다. "무엇을 사야 할지 모르는" 초보자는 첫 칸에서 막히고, 이는 REQ-05("처음 들어온 사람이 무엇을 눌러야 하는지 알 수 있어야 한다")에 정면으로 어긋납니다. 목록에서 고르는 길과 검색하는 길을 나란히 둡니다.
>
> 순위는 **코스피 거래대금 순**입니다. 두 가지를 실측으로 정했습니다.
>
> | 설정 | KIS 30건 중 `stocks` 일치 | 목록에 뜨는 것 |
> |---|---:|---|
> | 거래량순 · 전체시장 | 7건 | 동전주·ETF |
> | 거래대금순 · 전체시장 | 21건 | 대형주 + 코스닥 섞임 |
> | **거래대금순 · 코스피** (채택) | **29건** | 대형주 |
>
> `stocks` 테이블이 357종목 전부 코스피이므로, 시장을 코스피로 좁히지 않으면 우리가 주문할 수 없는 종목이 30칸 중 아홉 자리를 먹습니다. 우선주·ETF·ETN도 제외합니다. **KIS 호출은 1회**이고, 15초 캐시 + 동시요청 합치기로 `EGW00201`(초당 거래건수 초과)을 막습니다 — 캐시 없이는 새로고침 두 번에 바로 걸렸습니다.

> ⚠️ **AI 해석에 매수·매도 권유가 포함되어서는 안 됩니다.** "지금 사세요"가 아니라 "이 숫자는 이런 의미입니다"까지입니다. 프롬프트에 명시적으로 금지하고, [[../05_Scope/02_definition_of_done|완료 기준]]에서 30건을 검사합니다.
>
> 🔴 **인기 목록에는 이 금지선이 더 미묘하게 걸립니다.** "인기"는 거래대금이라는 사실을 옮긴 것일 뿐, 좋은 종목이라는 뜻이 아닙니다. 그래서 목록에 추천·별점·"주목" 같은 말을 쓰지 않고 **`거래대금 순`이라고 기준을 그대로 적어 둡니다.**

> 🔴 **정량지표에는 금지선이 하나 더 붙습니다.** PER·PBR은 "높다·낮다"까지만 말하고 **비싸다·싸다 또는 고평가·저평가로 단정하지 않습니다.** 값의 크기를 평가로 바꾸는 순간 종목 추천이 되기 때문입니다. 프롬프트가 "같은 값이라도 업종과 시점에 따라 해석이 달라진다"를 반드시 덧붙이게 합니다.

> 🔴 **음수 PER은 AI 해석이 반드시 짚어야 하는 지점입니다.** 적자 기업(예: 삼성SDI, EPS -8,325원)은 PER이 -51.29로 나옵니다. 계산 자체는 맞지만 **크기의 방향이 직관과 반대**입니다 — 적자가 작을수록 EPS가 0에 가까워 PER이 -500처럼 커지고, 적자가 클수록 -5처럼 작아집니다. 초보자는 마이너스를 "아주 낮다 = 싸다"로 읽기 쉽습니다.
>
> **그럼에도 값을 가리지 않는 이유**: 증권사 앱(토스 등)이 음수를 그대로 보여주고, 무엇보다 이 서비스의 일관된 패턴이 **"숫자는 그대로 두고 AI가 해석한다"**이기 때문입니다(계좌 화면도 동일). 값을 숨기면 이 패턴이 깨지고 정보도 잃습니다. 대신 프롬프트가 "PER 공식이 성립하지 않는다", "마이너스라서 저렴한 것이 아니다"를 반드시 말하게 합니다.

> 💡 지표는 **추가 API 호출 없이** 얻습니다. KIS 현재가 조회(`FHKST01010100`) 응답에 `per`·`pbr`·`eps`·`bps`·`w52_hgpr`·`w52_lwpr`가 이미 들어 있습니다. PSR은 응답에 없어(매출액 미제공) 범위에서 제외했습니다. 그래프만 일봉 조회(`FHKST03010100`)를 한 번 더 쓰고, **종목+구간별로 60초 캐시**를 둡니다.

> 🆕 **그래프에 캔들·이동평균선·거래량 막대를 넣지 않았습니다.** 이 서비스의 사용자는 그 기호를 읽지 못하고, 읽는 법을 가르치는 것은 범위 밖입니다. "요즘 오르는 중인지 내리는 중인지" 한 가지만 종가 선으로 전달합니다. 마찬가지로 `52주 범위`도 숫자만 주면 사용자가 위치를 직접 계산해야 하므로 **막대 위의 점**으로 보여줍니다.

> 🆕 **일·주·월·년 토글은 같은 API의 `FID_PERIOD_DIV_CODE`만 바꿔서 씁니다.** 새 엔드포인트가 아니라 `/api/chart`에 `period` 쿼리 하나가 늘었을 뿐입니다. 요청 범위와 실제로 오는 봉 수는 다릅니다 — KIS가 한 번에 최대 100개까지만 주기 때문입니다.
>
> | 구간 | 요청 범위 | 실측 수신량 |
> |---|---|---:|
> | 일 | 3개월 | 62개(거래일만) |
> | 주 | 2년 | 100개 |
> | 월 | 10년 | 100개 |
> | 년 | 20년 | 21개(상장 후 전체) |

> 🆕 **수량 입력에 `10%·25%·50%·최대` 버튼을 둡니다.** 남은 예산으로 몇 주를 살 수 있는지 나눗셈을 사용자에게 시키지 않기 위해서입니다. 이 값은 KIS를 부르지 않는 `/api/budget`에서 받습니다 — 예산 한 줄 때문에 `/api/account`를 부르면 보유 종목 수만큼 KIS 시세를 조회하게 되어 시세·그래프 호출과 겹쳐 한도에 걸립니다.

### 흐름 D. 매수 주문 — `/trade` (핵심 흐름)

프로젝트 2에서 4턴이던 것이 **1화면 3단계**가 됩니다.

```
[1단계] 입력  — 같은 화면
1. 시세가 표시된 상태에서 수량을 입력합니다.
2. 예상 주문금액이 실시간으로 계산되어 표시됩니다.
3. 근거 선택지 6개가 라디오 버튼으로 표시됩니다.
4. 메모 입력란(선택)이 있습니다.
5. 🔴 근거를 고르기 전에는 [주문하기] 버튼이 비활성화 상태입니다.

[2단계] 확인 — 모달
6. [주문하기]를 누릅니다.
6-a. 🔴 로그인하지 않았다면, 확인 모달 대신 **"Google로 계속하기"** 버튼이 뜹니다. 로그인 후 같은 확인 모달로 자동 이어집니다.        ← 예외 2.10
7. 확인 모달이 열립니다.
   "삼성전자 10주 · 예상 682,000원 · 근거: 실적이 좋아짐 · 이 주문 후 남는 예산 4,318,000원"
8. [확인]을 누릅니다.

[3단계] 실행 — 서버
9.  서버가 세션에서 로그인된 사용자의 user_id를 확인합니다. (미로그인이면 401)
10. 서버가 user_wallets를 조회합니다. (첫 주문이면 생성 + 기본 예산 500만원 지급)
11. 서버가 사전 검증을 수행합니다.
    · 장 운영시간인가                              ← 예외 2.4
    · 실제 계좌 예수금이 충분한가                     ← 예외 2.5
    · 진행 중인 주문이 있는가                        ← 예외 2.6
    · 🔴 사용자의 가상 예산을 초과하는가              ← 예외 2.11
12. orders 행을 status='requested'로 생성합니다. (user_id 포함)
13. rationales 행을 저장합니다.
14. KIS 매수주문을 호출합니다.
15-a. 성공 → orders를 status='submitted', order_no 갱신
15-b. 실패 → orders를 status='rejected', reject_reason 기록    ← 예외 2.8
16. 결과를 화면에 표시하고 [회고 화면에서 보기] 링크를 제공합니다.
17. 이벤트를 기록합니다.
```

### 🔴 왜 패스코드가 아니라 로그인 + 가상 예산으로 계좌를 지킵니까?

이전 설계는 "소유자만 주문 가능"이었습니다. 지금은 **누구나 로그인만 하면 주문할 수 있되, 각자 쓸 수 있는 금액에 한도**를 둡니다.

```
정식 서비스: 사용자마다 실제 계좌를 배정 (물리적 분리)
이번 MVP:   계좌 1개 + 사용자별 가상 예산 500만원 (논리적 분리, 로그인으로 신원 확정)
```

이렇게 바꾼 이유는 REQ-04("링크를 받은 사람이 바로 쓸 수 있어야 한다")를 **주문까지 포함해** 완전히 만족시키기 위해서입니다. 패스코드로 막으면 사용자는 "체험만" 하고 진짜 주문은 못 해봅니다. **로그인은 계좌를 지키기 위한 잠금장치가 아니라, 예산·기록을 지속시키기 위한 신원 확인**입니다.

### 🔴 왜 근거를 주문 **전에**, 그리고 **DB 저장 순서상으로도 먼저** 받습니까?

| 시점 | 결과 |
|---|---|
| 주문 후 요청 | 주문이 끝났으므로 사용자가 답하지 않고 이탈합니다 |
| 주문 전 요청 (채택) | 주문을 하려면 근거를 지나가야 합니다. **근거 기록률이 구조적으로 100%가 됩니다** |

12번이 13번보다 앞에 있는 것도 의도적입니다. KIS 호출이 실패해도 **사용자가 근거를 만들었다는 사실은 유효**하므로 기록에 남깁니다.

---

### 흐름 E. 근거 회고 — `/journal` 🆕

**웹에서만 가능한 흐름입니다.**

```
1. 사용자가 [지난 근거 보기]를 누릅니다.
2. 서버가 orders와 rationales를 조인해 최신순으로 가져옵니다.
3. 각 행에 다음을 표시합니다.
   종목 / 수량 / 주문일 / 당시 가격(expected_price) / 근거 유형 / 메모 / 주문 상태
4. 서버가 보유 종목의 현재가를 KIS에서 가져와 당시가와 대비해 표시합니다.
5. 상단에 집계를 표시합니다.
   총 주문 n건 · 근거 기록률 100% · "그냥 감" 비율 n%
6. 사용자가 [내 근거 되돌아보기]를 누릅니다.
7. 서버가 근거 목록 전체를 Gemini에 넘겨 회고 코멘트를 생성합니다.   ← AI-2
8. 코멘트를 상단에 표시합니다.
9. journal_reviewed 이벤트를 기록합니다.
```

### AI-2가 하는 일 (그리고 하지 않는 일)

| 한다 | 하지 않는다 |
|---|---|
| 근거 유형의 편중을 짚습니다 ("6건 중 4건이 뉴스입니다") | 종목을 추천하지 않습니다 |
| 메모가 비어 있는 비율을 짚습니다 | 수익률을 예측하지 않습니다 |
| 같은 근거로 산 종목들의 공통점을 정리합니다 | "이건 잘못된 판단이었습니다"라고 평가하지 않습니다 |
| 다음에 물어볼 질문을 1개 제안합니다 | 매수·매도 시점을 말하지 않습니다 |

> **평가가 아니라 되비추기(reflection)입니다.** 평가를 하면 유사투자자문 영역에 접근하고, 사용자가 AI 의견을 따라가면 이 프로젝트의 목적(자기 판단을 설명하게 하기)과 정반대가 됩니다.

## 2. 예외 업무 흐름

작성 순서: `무엇이 실패했는가 → 상태를 어떻게 하는가 → 무엇을 안내하는가 → 재시도 가능한가 → 무엇을 기록하는가`

### 2.1 🔴 KIS 토큰 발급 실패 / 만료

```
KIS 호출이 인증 오류를 반환합니다.
→ kis_tokens 캐시를 무효화하고 재발급을 1회 시도합니다.
→ 성공하면 원래 요청을 재시도합니다. 사용자에게 알리지 않습니다.
→ 실패하면 "계좌 정보를 불러오지 못했습니다. 잠시 후 다시 시도해주세요."
→ 재시도 가능합니다.
→ token_refreshed 또는 token_refresh_failed 이벤트를 기록합니다.
```

> 🔴 **재발급을 무한 재시도하지 않습니다.** 서버리스에서 실패 루프는 그대로 요청 폭주가 됩니다. **1회만** 재시도합니다.

### 2.2 종목명이 모호함

```
"삼성전자" 검색 결과가 2건 이상입니다. (삼성전자 / 삼성전자우)
→ 시세를 조회하지 않습니다. 임의로 고르지 않습니다.
→ 후보 목록을 버튼으로 제시합니다.
→ 사용자가 고르면 이어집니다.
→ stock_ambiguous 이벤트를 기록합니다.
```

> **임의 선택 금지.** 주문은 되돌릴 수 없으므로 시스템이 종목을 추측하면 안 됩니다.

### 2.3 종목을 찾을 수 없음

```
검색 결과가 0건입니다.
→ "코스피 상위 100종목만 지원합니다. 다른 종목명으로 검색해보세요."
→ 지원 종목 예시 5개를 함께 보여줍니다.
→ 재시도 가능합니다.
→ stock_resolution_failed 이벤트를 입력값과 함께 기록합니다.
```

> 예시를 함께 보여주는 이유: "찾을 수 없습니다"만 있으면 사용자가 무엇을 해야 할지 모릅니다. (REQ-05)

### 2.4 장 운영시간이 아님

```
평일 09:00~15:30 밖에서 주문을 시도합니다.
→ 주문을 접수하지 않습니다. orders 행을 만들지 않습니다.
→ "지금은 장 운영시간이 아닙니다. 평일 09:00~15:30에 주문할 수 있습니다.
   계좌 확인과 종목 조회는 지금도 가능합니다."
→ 장이 열리면 재시도 가능합니다.
→ order_rejected_market_closed 이벤트를 기록합니다.
```

> 🔴 **조회 흐름(B·C·E)은 장 시간 밖에도 동작해야 합니다.** Day 3·4가 휴장일이므로, 이 조건이 지켜지지 않으면 이틀 동안 아무것도 테스트할 수 없습니다.

### 2.5 예수금 부족

```
예상 주문금액이 예수금을 초과합니다.
→ 주문을 접수하지 않습니다.
→ "예수금이 부족합니다. 현재 OOO원, 필요 OOO원. 수량을 줄여보세요."
→ 수량을 바꿔 재시도 가능합니다.
→ order_rejected_insufficient_funds 이벤트를 기록합니다.
```

### 2.6 중복 주문

```
같은 종목·같은 수량 주문이 60초 안에 다시 들어옵니다. (더블 클릭 등)
→ 새 주문을 만들지 않습니다.
→ "방금 같은 주문을 넣었습니다. 회고 화면에서 확인해보세요."
→ duplicate_order_blocked 이벤트를 기록합니다.
```

> 프로젝트 2는 부분 유니크 인덱스로 막았습니다. 웹에서는 **① 제출 직후 버튼 비활성화 ② 서버에서 60초 내 동일 주문 조회**의 2중으로 막습니다. 대기 상태가 없으므로 인덱스 조건이 단순해집니다.

### 2.7 AI 호출 실패 (REQ-05 직결)

```
Gemini 호출이 실패하거나 시간을 초과합니다.
→ 화면을 깨뜨리지 않습니다. 원본 수치는 그대로 유지합니다.
→ AI 영역에만 "해석을 준비하지 못했습니다. [다시 시도]"를 표시합니다.
→ 주문 흐름에서는 AI를 호출하지 않으므로 주문은 영향받지 않습니다.
→ llm_call_failed 이벤트를 기록합니다.
```

> 🔴 **주문 경로에 AI를 넣지 않은 것이 설계상 중요합니다.** AI가 죽어도 핵심 기능인 주문과 근거 기록은 동작합니다. 발표 중 Gemini가 느려져도 시연이 멈추지 않습니다.

### 2.8 KIS가 주문을 거부함

```
주문 API가 실패 응답을 반환합니다.
→ orders.status = 'rejected', reject_reason에 KIS 메시지를 저장합니다.
→ 이미 저장한 rationales는 삭제하지 않습니다.
→ "주문이 거부되었습니다. 사유: OOO. [다시 시도]"
→ order_rejected 이벤트를 기록합니다.
```

### 2.9 입력이 비어 있음 (REQ-05 직결)

```
수량이 0이거나 비어 있음 / 근거를 고르지 않음 / 검색어가 비어 있음
→ 서버를 호출하지 않습니다.
→ 해당 입력란 아래에 무엇이 필요한지 한 줄로 표시합니다.
→ [주문하기] 버튼은 비활성화 상태를 유지합니다.
→ 이벤트를 기록하지 않습니다. (사용자의 정상적인 입력 과정입니다)
```

> **요청서 REQ-05가 명시적으로 요구하는 항목입니다.** "입력이 비었을 때 화면이 깨지지 않아야 합니다."

### 2.10 로그인하지 않고 주문을 시도함

```
로그인하지 않은 사용자가 [주문하기]를 누릅니다.
→ KIS를 호출하지 않습니다. orders 행을 만들지 않습니다.
→ 확인 모달 대신 "Google로 계속하기" 버튼을 보여줍니다.
→ 로그인에 성공하면 방금 작성하던 주문 폼(종목·수량·근거)이 그대로 유지된 채 확인 모달로 이어집니다.
→ 로그인 자체는 실패로 기록하지 않습니다. (정상적인 진입 과정입니다)
```

> 조회 화면(계좌·종목·회고)은 로그인 없이도 전부 볼 수 있습니다. **로그인은 주문 실행 시점에만 요구됩니다.** ([[02_user_roles|사용자 역할]] 2절)

### 2.11 🔴 가상 예산 초과

```
사용자의 누적 주문 금액 + 이번 주문 예상금액이 할당된 가상 예산(기본 500만원)을 초과합니다.
→ 실제 계좌 예수금과 무관하게 주문을 접수하지 않습니다. orders 행을 만들지 않습니다.
→ "가상 예산을 초과했습니다. 남은 한도 OOO원. 수량을 줄여보세요."
→ 수량을 바꿔 재시도 가능합니다.
→ order_rejected_budget_exceeded 이벤트를 user_id와 함께 기록합니다.
```

> 실제 계좌 예수금(예외 2.5)과 가상 예산(이 예외)은 서로 다른 검사입니다. **가상 예산이 사용자별 1차 방어선**이고, 실제 예수금 확인이 계좌 전체를 지키는 최종 방어선입니다. ([[02_user_roles|사용자 역할]] 4절)

### 2.12 Supabase 조회 실패

```
DB 호출이 실패합니다.
→ 화면을 깨뜨리지 않습니다.
→ "기록을 불러오지 못했습니다. [다시 시도]"
→ 재시도 가능합니다.
→ 서버 로그에만 남깁니다. (event_logs도 같은 DB이므로 기록 시도하지 않습니다)
```

## 4. 주문 상태 흐름

```
requested → submitted        (KIS 접수 성공)
requested → rejected         (사전 검증 실패 또는 KIS 거부)
```

프로젝트 2의 `awaiting_confirmation` / `awaiting_rationale` / `expired`가 **사라졌습니다.** 폼 제출이 원자적이기 때문입니다. 상태가 8개에서 2개로 줄었고, 만료 정리 로직도 사라졌습니다.

`executed`는 체결 조회를 범위에서 제외했으므로 사용하지 않습니다.
