### 🔄 상태코드가 계획과 크게 다릅니다

원래 계획은 검증 실패마다 4xx를 돌려주는 것이었습니다. 실제로는 **대부분 HTTP 200 + `{ok:false, code}`**입니다.

| 단계 | 계획 | 실제 | 왜 |
|---|---|---|---|
| ③ 장 시간 | ~~422~~ | **200** `code:"market_closed"` | 예외 2.7과 같은 원칙 — 화면이 "네트워크 오류"와 "업무 규칙에 걸림"을 구분할 필요가 없게 만들었습니다. 4xx는 브라우저·프록시·모니터링이 각자 다르게 해석합니다 |
| ④ 종목 확인 | ~~404~~ | **400** `code:"invalid_input"` | 종목코드는 사용자가 고른 값이 아니라 **화면이 보낸 값**입니다. 없는 종목이 오면 "리소스가 없다"가 아니라 "요청이 잘못됐다"가 맞습니다 |
| ⑤ 중복 | ~~409~~ | **200** `code:"duplicate"` | 위와 같음 |
| ⑨ 가상 예산 / 보유수량 | ~~422~~ | **200** `code:"budget_exceeded"` / `"oversell"` | 위와 같음 |
| ⑩ 실제 예수금 | ~~422~~ | **200** `code:"insufficient_funds"` | 위와 같음 |
| ⑬ KIS 거부 | — | **200** `code:"kis_rejected"` | 위와 같음 |
| ①②⑥⑪ | 400 / 401 / 502 / 500 | **400 / 401 / 502 / 502** | ⑪(orders INSERT 실패)만 계획의 500이 아니라 502입니다 |

> ⚠️ **⑦ `user_wallets` upsert는 결과를 검사하지 않습니다.** 계획(3번 "실패: 500")과 다릅니다. `ignoreDuplicates: true`로 넣고 반환값을 보지 않으므로, **upsert가 실패해도 주문은 그대로 진행됩니다.** 그래도 큰 사고가 안 나는 이유는 `getMyPortfolio`가 지갑 행이 없을 때 기본 예산(500만원)을 그대로 쓰기 때문입니다 — 즉 실패해도 "예산이 없어서 못 산다"가 아니라 "기본 예산으로 산다"가 됩니다. **의도한 설계라기보다 그렇게 되어 있는 것에 가깝고, 정리하지 않았습니다.**

### 🔴 1·2단계에 서버 호출이 없다는 것이 중요합니다

프로젝트 2에서는 확인 단계(2턴)와 근거 입력(3턴)이 각각 DB 왕복이었고, 그 사이에 대기 상태와 만료 관리가 필요했습니다.

**웹에서는 사용자가 폼을 채우는 동안 서버가 아무것도 모릅니다.** 그래서:

| 사라진 것 | 개발 시간 절감 |
|---|---:|
| `awaiting_confirmation` 상태 | — |
| `awaiting_rationale` 상태 | — |
| `expires_at` 만료 정리 | -1.5h |
| 대기 상태 조회·복원 로직 | -2h |

> 🔄 **이 절의 제목이 절반만 맞습니다.** **1단계는 지금도 서버 호출이 0회**이고, 위 표의 "사라진 것"도 그대로 사라진 채입니다 — 서버는 여전히 대기 상태를 들고 있지 않고, 만료 정리도 없습니다.
>
> **하지만 2단계에는 서버 호출이 생겼습니다.** `openConfirm()`이 모달을 띄우기 **전에** `GET /api/budget`을 부릅니다(`components/TradeFlow.tsx`). 확인 모달이 "이 주문 후 남는 예산 OOO원"을 보여주려면 그 숫자가 필요한데, 화면이 오래 열려 있었다면 처음 받아둔 값이 이미 낡았기 때문입니다.
>
> **그래도 "상태"는 안 생겼습니다.** `/api/budget`은 **읽기 전용**이고 KIS도 부르지 않습니다(`lib/portfolio.ts`의 Supabase 조회뿐). 서버는 여전히 "이 사용자가 지금 주문을 만들고 있다"는 사실을 모릅니다. 사라진 것은 **대기 상태**였지 **모든 서버 호출**이 아니었는데, 그걸 "서버 호출 없음"이라고 뭉뚱그려 적은 것이 이 문장의 잘못입니다.

### 🔴 그 대신 생긴 위험

**클라이언트에서 계산한 예상금액을 서버가 믿으면 안 됩니다.**

```
❌ POST /api/order { expectedAmount: 682000 }  → 서버가 그대로 사용
✅ POST /api/order { stockCode, qty }          → 서버가 시세를 다시 조회해 계산
```

브라우저에서 온 값은 조작될 수 있습니다. **⑥에서 서버가 시세를 다시 조회하는 것은 중복이 아니라 검증입니다.**

> ⚠️ **이 원칙은 시장가에서만 지켜집니다 — 알려진 한계입니다.**
>
> 지정가 주문에서는 서버가 **클라이언트가 보낸 `limitPrice`를 그대로 씁니다.** 검증하는 것은 **호가단위 배수인지(`isValidTickPrice`)와 정수인지**뿐이고, **현재 시세와 대조하지 않습니다.** 즉 삼성전자를 1,000원 지정가로 주문하는 요청을 서버가 막지 않습니다.
>
> **왜 이렇게 뒀는가**: 지정가의 존재 이유가 "지금 시세와 다른 가격에 걸어두는 것"이라, "시세에서 얼마나 벗어나면 거부할 것인가"를 정하려면 상·하한가 규칙까지 들어와야 했습니다. 4일 안에 그 규칙을 정확히 넣을 자신이 없었습니다.
>
> **지금 실제 피해가 크지 않은 이유**: ① 터무니없는 가격은 KIS가 상·하한가로 거부하고, ② 가상 예산은 `limitPrice × 수량`으로 묶이므로 **낮은 가격을 넣으면 자기 예산만 적게 묶일 뿐** 계좌를 더 쓸 수는 없습니다. **다만 "가격을 서버가 검증한다"는 이 절의 원칙 자체가 지정가에서는 깨져 있고, 그 사실을 숨기지 않습니다.** ([[../07_Submit/02_scope_reduction|범위 축소 설명서]] 6절 "새로 생긴 한계"에도 같은 항목이 있습니다)

## 4. 흐름 E — 회고

> 🔄 **KIS를 부르는 주체가 다릅니다.** 원래 그림은 Server Component가 현재가까지 받아 HTML을 완성하는 모양이었는데, 실제로는 서버가 저장된 데이터만 그리고 **현재가는 클라이언트가 따로 가져옵니다.**

```
브라우저                Server Component      Supabase        KIS
   ├─ GET /journal ────────>│                    │             │
   │                        ├─ orders ⨝ rationales (RLS가 본인 행만) ─>│
   │                        │<─ 내 주문 전체 ─────────┤         │
   │<─ HTML (표 + 집계 + 근거) ─┤   🔴 여기서 KIS를 부르지 않습니다
   │
   │  [근거·당시가·집계가 이미 화면에 있음 — 여기까지 외부 API 0회]
   │
   ├─ (JournalList가 마운트되면) POST /api/quotes ─>│
   │   { codes: [...최대 20종목] }                  ├─ getQuotes ──>│
   │                                                │<─ 현재가 ─────┤
   │<─ { prices, truncated, timedOut } ─────────────┤
   │
   │  [당시가 vs 현재가 대조가 그 위에 얹힘 — 여기까지 AI 없음]
   │
   ├─ [내 근거 되돌아보기] 클릭
   ├─ POST /api/ai/review ─>│                            Gemini
   │                        ├─ 최근 20건 근거 목록 ──────────>│
   │                        │<─ 회고 코멘트 3~4문장 ──────────┤
   │                        ├─ logEvent(journal_reviewed) ─>│
   │<─ 코멘트 ──────────────┤
```

**왜 이렇게 됐는가**: Server Component 안에서 KIS를 부르면 **현재가를 다 받을 때까지 화면이 한 글자도 안 나옵니다.** 종목이 10개면 KIS 전역 큐(초당 1건, [[02_architecture|아키텍처]] 4b절) 때문에 최소 10초가 넘어가고, 그동안 회고 화면은 흰 화면입니다. **회고 화면을 시연의 최종 안전판으로 삼기로 한 이상, 그 화면이 외부 API를 기다리게 두면 안 됐습니다.**

- 서버가 그리는 것: `components/JournalList.tsx`에 넘길 행 + `Summary`(총 주문·근거 기록·그냥 감 건수)
- 클라이언트가 얹는 것: 현재가와 등락률 (`POST /api/quotes`, 최대 20종목)

### 🔴 KIS 현재가 조회를 실패해도 화면이 나옵니다

```
현재가 조회 성공 → 당시 68,000원 → 현재 71,200원 (+4.7%)
현재가 조회 실패 → 당시 68,000원 → 현재 —
```

**회고 화면은 저장된 데이터만으로도 성립합니다.** KIS와 Gemini가 모두 죽어도 근거 목록과 집계는 보입니다. `/api/quotes`는 개별 종목이 실패해도 그 종목만 `null`로 두고 **200으로 응답**합니다.

> 🔴 **그래서 회고 화면이 발표 시연의 최종 안전판입니다.** 다른 모든 것이 실패해도 이 화면 하나로 "이 서비스가 무엇을 하는지"를 보여줄 수 있습니다. **구조가 계획보다 오히려 더 안전한 쪽으로 갔습니다** — 계획에서는 Server Component가 KIS를 기다렸는데, 지금은 KIS가 아예 렌더링 경로 밖에 있습니다.

## 5. 실패 전파 정리

| 실패 지점 | 전파 범위 | 사용자에게 보이는 것 |
|---|---|---|
| Gemini | 해당 AI 영역만 | 숫자·표는 그대로, AI 자리에 재시도 버튼 (`/api/ai/*`가 200 + `ok:false`) |
| KIS 시세 (`/api/quote`) | 해당 종목 화면만 | "시세를 불러오지 못했습니다" + 주문 폼 비활성화 |
| 🔄 KIS 토큰 | ~~계좌·시세·주문 전부~~ **주문·시세·인기목록** | 회고 화면은 정상. **계좌 화면도 목록·예산은 그대로 나옵니다**(아래) |
| Supabase | 검색·주문·회고 | "기록을 불러오지 못했습니다" |
| 로그인 안 함 | 주문만 | Google 로그인 버튼 (조회·회고는 그대로 열람 가능) |
| 가상 예산 초과 | 주문만 | 남은 한도 안내 + 회고 화면 링크 |
| 🆕 보유수량 초과 (매도) | 주문만 | "지금 팔 수 있는 수량은 N주입니다" |
| 🆕 KIS 차트 (`/api/chart`) | 차트만 | 캐시가 있으면 옛 차트(`stale`), 없으면 차트 영역이 조용히 사라짐 |
| 🆕 KIS 배당·재무 | 해당 카드만 | 캐시가 있으면 옛 값, 없으면 빈 배열 → 카드가 안 그려짐 |
| 🆕 DART·구글 뉴스 | 공시뉴스 탭과 AI-1 재료만 | 빈 배열(`lib/dart.ts`·`lib/news.ts`가 throw하지 않음). AI 해석은 시세만으로 나갑니다 |

> 🔄 **"KIS 토큰 실패 → 계좌 정보를 불러오지 못했습니다"는 틀렸습니다.**
> `app/api/account/route.ts`는 **KIS 실패를 삼킵니다.** 시세 조회(`getQuotes`)를 try/catch로 감싸 실패해도 로그만 남기고, 보유 목록·가상 예산·대기 주문을 **200으로 그대로 응답**합니다. 현재가 자리만 `—`가 되고 `partialPrices: true`가 붙습니다.
> 502가 나가는 경우는 KIS가 아니라 **`getMyPortfolio`(Supabase) 실패뿐**입니다.
> **의도한 대로 동작하고 있고, 문서만 늦었습니다** — REQ-05의 "AI·외부 API가 실패해도 화면이 안 깨진다"를 계좌 화면에서도 지킨 결과입니다.

**어느 칸에도 "화면이 하얗게 됨"이 없어야 합니다.** ([[../05_Scope/02_definition_of_done|완료 기준]] REQ-05 항목)

## 6. 이 문서에서 확정한 설계 결정 5가지

| # | 결정 | 근거 | 실제 |
|---:|---|---|---|
| 1 | AI 호출을 별도 왕복으로 분리 | AI 실패가 화면을 깨뜨리지 않게 (REQ-05) | ✅ 그대로 |
| 2 | 근거 저장이 KIS 주문보다 앞 | 주문이 실패해도 근거는 남아야 함 | ✅ 그대로 (⑫가 ⑬보다 앞) |
| 3 | 예상금액을 서버가 재계산 | 클라이언트 값은 신뢰하지 않음 | ⚠️ **시장가만.** 지정가는 클라이언트 `limitPrice`를 그대로 씀 (3절 참고) |
| 4 | ~~가상 예산 검증이 실제 계좌 검증 뒤, KIS 호출 전~~ | ~~로그인 사용자별 한도로 계좌 1개를 안전하게 공유~~ | 🔄 **순서가 반대가 됐습니다** (아래) |
| 5 | 회고 화면은 외부 API 없이도 렌더링 | 시연 안전판 확보 | ✅ 그대로 (계획보다 더 철저해짐 — 4절) |

### 🔄 결정 #4가 뒤집혔습니다 — 가상 예산이 실제 예수금보다 **앞**입니다

**계획**: 실제 예수금(계좌 전체) → 가상 예산(사용자 개인).
근거는 *"계좌 자체가 부족하면 사용자 한도를 볼 필요도 없다"*였습니다.

**코드**(`app/api/order/route.ts`): 가상 예산 → 실제 예수금. 주석에 근거가 명시돼 있습니다.

> *"가상 예산을 실제 예수금보다 먼저 보는 이유는, 가상 예산이 '사용자 1명이 계좌를 몰아 쓰는 것'을 막는 1차 방어선이고 실제 예수금 확인은 계좌 전체를 지키는 최종 방어선이기 때문입니다."*

**어느 판단이 옳았는가 — 코드가 옳았습니다.** 이유는 두 가지이고, 둘 다 계획 시점에 못 본 것입니다.

| | 계획(예수금 먼저) | 코드(예산 먼저) |
|---|---|---|
| **KIS 호출 비용** | 예산 초과가 뻔한 요청에도 `getBuyableCash`(KIS 1회)를 **반드시** 부릅니다. 전역 큐(초당 1건) 때문에 그 자체로 최소 1.1초를 태우고, 다른 사용자의 시세·차트 호출을 그만큼 밀어냅니다 | 예산에서 걸리면 **KIS를 아예 안 부릅니다.** 같은 문서가 "싼 검증을 먼저"라고 적어놓고 정작 가장 비싼 검증을 앞에 뒀던 것입니다 |
| **누구의 잘못을 먼저 알려주는가** | 사용자가 자기 한도를 넘겼는데 "계좌 예수금이 부족합니다"를 먼저 봅니다. **자기가 고칠 수 없는 사유**입니다 | "가상 예산을 초과했습니다. 남은 한도 OOO원, 수량을 줄여보세요" — **사용자가 바로 고칠 수 있는 사유**입니다 |

**계획의 근거였던 "계좌가 부족하면 개인 한도를 볼 필요도 없다"는 왜 틀렸는가**: 이 서비스에서 **계좌가 부족한 상황은 개인 한도를 다 쓰기 전에는 거의 오지 않습니다.** 가상 예산 500만원 × 사용자 수가 계좌 예수금을 넘어야 비로소 예수금이 먼저 걸리는데, 그건 사용자가 많아졌을 때의 이야기이고 **평시에는 예산이 항상 먼저 걸립니다.** 즉 계획은 "드물게 일어나는 실패"를 "매번 일어나는 실패"보다 앞에 두고 있었습니다.

> 🔴 **두 검증이 서로 다른 것을 지킨다는 원래 문장은 지금도 맞습니다.** 예산 검증이 없으면 한 사용자가 계좌를 몰아 쓰고, 예수금 검증이 없으면 계좌 전체가 위험합니다. **바뀐 것은 "무엇을 지키는가"가 아니라 "어느 쪽을 먼저 물어보는가"뿐입니다.** 두 검증 모두 그대로 있습니다.
>
> ⚠️ **단, 매도에는 실제 예수금 검증이 아예 없습니다.** 파는 데는 현금이 필요 없어 설계상 의도한 것이지만(`lib/kis.ts`의 `placeSellOrder` 주석), **검증 경로가 매수와 완전히 갈라졌다는 사실**은 기록해둡니다. 매도의 한도는 "이 서비스로 실제 보유한 수량"(`availableToSell`)이고, 그마저도 **공유 모의계좌의 실제 잔고와는 대조하지 않습니다** — KIS가 거부하면 그 거부를 그대로 사용자에게 전달합니다.
