## 1. 흐름 B — 계좌 확인

> 🔄 **2026-08-06 변경.** 공용 KIS 모의계좌 잔고조회를 직접 쓰지 않습니다. 다른 방문자의 주문·이전 보유 종목이 섞여 나오는 문제 때문에, `orders` 기준 내 주문만 합산하는 방식으로 바뀌었습니다 ([[../02_Domain/03_workflow|업무 흐름]] 흐름 B).

```
브라우저                Route Handler           Supabase          KIS
   │                        │                     │               │
   ├─ GET /api/account ────>│                     │               │
   │                        ├─ auth.getUser ─────>│               │
   │                        │<─ user (없으면 loggedIn:false 즉시 응답)│
   │                        ├─ getMyPortfolio ───>│               │
   │                        │  (orders 합산, 거부 제외, 지갑 미생성 시 500만원)
   │                        │<─ 보유종목/가상예산 ─┤               │
   │                        │  (보유 종목 있으면) getQuotes ───────>│
   │                        │<─ 현재가 (일부 실패해도 계속) ─────────┤
   │                        ├─ logEvent ─────────>│               │
   │<─ JSON ────────────────┤                     │               │
   │                                                              │
   │  [화면에 표 렌더링 — 여기까지 AI 없음]                          │
   │                                                              │
   ├─ 사용자가 [이게 무슨 뜻인가요?] 클릭                            │
   ├─ POST /api/ai/explain ─>│                    │      Gemini   │
   │                         ├─ 프롬프트 + 내 예산/보유 JSON ──────>│      │
   │                         │<─ 해석 4문장 ───────────────┤      │
   │<─ 해석 문장 ────────────┤                                    │
```

### 🔴 AI 호출을 두 번째 왕복으로 분리한 이유

| 방식 | 첫 화면까지 | AI 실패 시 |
|---|---:|---|
| 한 번에 처리 | 3~6초 | 🔴 **화면 전체가 실패** |
| 2단 분리 (채택) | 1초 | ⚠️ 숫자는 이미 보임 |

**REQ-05가 요구하는 "AI 호출이 실패해도 화면이 깨지지 않아야 한다"를 아키텍처로 만족합니다.** try/catch로 막는 것이 아니라, AI가 없어도 화면이 완성되도록 구조를 나눴습니다.

## 2. 흐름 C — 종목 조회

```
브라우저                Route Handler        Supabase        KIS
   ├─ GET /api/stocks?q=삼성 ──>│              │             │
   │                            ├─ ilike 검색 ─>│             │
   │                            │<─ 후보 n건 ───┤             │
   │<─ 후보 목록 ───────────────┤                             │
   │
   │  n = 0 → "코스피 100종목만 지원합니다" + 예시     (예외 2.3)
   │  n > 1 → 후보 버튼 표시, 사용자가 선택           (예외 2.2)
   │  n = 1 → 자동으로 다음 단계
   │
   ├─ GET /api/quote?code=005930 ─>│            │             │
   │                                ├─ 시세조회 ───────────────>│
   │                                │<─ 현재가/등락률/거래량 ────┤
   │<─ JSON ────────────────────────┤
   │
   │  [표 렌더링 → 주문 폼 활성화]
```

**종목 검색은 Supabase만 씁니다.** KIS를 부르지 않으므로 빠르고, KIS가 죽어도 검색은 동작합니다.

## 3. 🔴 흐름 D — 주문 (핵심)

```
브라우저                                Route Handler        Supabase       KIS
   │
   │ [1단계 — 서버 호출 없음]
   ├─ 수량 입력 → 예상금액 = 현재가 × 수량 (클라이언트 계산)
   ├─ 근거 라디오 선택
   │   └─ 미선택이면 [주문하기] disabled          (예외 2.9)
   │
   │ [2단계 — 서버 호출 없음]
   ├─ [주문하기]
   │   └─ 🔴 미로그인이면 확인 모달 대신 "Google로 계속하기" 표시  (예외 2.10)
   │       로그인 성공 → 폼 유지된 채 확인 모달로 복귀
   │   └─ 로그인 상태면 확인 모달 "이 주문 후 남는 예산 OOO원" 표시
   │
   │ [3단계]
   ├─ POST /api/order ──────────────────>│
   │   { stockCode, qty, reasonType,     │
   │     reasonMemo }  (user_id는 Auth 세션에서 확인, body에 없음)│
   │                                     ├─ ① 입력 검증
   │                                     ├─ ② 로그인 세션 확인 → 401 (예외 2.10)
   │                                     ├─ ③ user_wallets 조회/생성 ─>│
   │                                     ├─ ④ 장 시간 검증   → 422 (예외 2.4)
   │                                     ├─ ⑤ 종목 확인 ────>│
   │                                     ├─ ⑥ 시세 조회 ─────────────────>│
   │                                     ├─ ⑦ 예수금 검증 ───────────────>│
   │                                     │                   → 422 (예외 2.5)
   │                                     ├─ ⑧ 가상 예산 검증 ─>│
   │                                     │                   → 422 (예외 2.11)
   │                                     ├─ ⑨ 중복 검증 ────>│
   │                                     │                   → 409 (예외 2.6)
   │                                     ├─ ⑩ orders INSERT ─>│  (user_id 포함)
   │                                     ├─ ⑪ rationales INSERT >│  🔴 주문 前
   │                                     ├─ ⑫ 매수 주문 ─────────────────>│
   │                                     │<─ order_no 또는 오류 ───────────┤
   │                                     ├─ ⑬ orders UPDATE ─>│
   │                                     ├─ ⑭ logEvent ─────>│
   │<─ { ok, orderNo, message } ─────────┤
   │
   │  성공 → "주문이 접수되었습니다. 주문번호 OOO"
   │          + [회고 화면에서 보기] 링크
   │  실패 → 사유 표시 + [다시 시도]
```

### 🔴 1·2단계에 서버 호출이 없다는 것이 중요합니다

프로젝트 2에서는 확인 단계(2턴)와 근거 입력(3턴)이 각각 DB 왕복이었고, 그 사이에 대기 상태와 만료 관리가 필요했습니다.

**웹에서는 사용자가 폼을 채우는 동안 서버가 아무것도 모릅니다.** 그래서:

| 사라진 것 | 개발 시간 절감 |
|---|---:|
| `awaiting_confirmation` 상태 | — |
| `awaiting_rationale` 상태 | — |
| `expires_at` 만료 정리 | -1.5h |
| 대기 상태 조회·복원 로직 | -2h |

### 🔴 그 대신 생긴 위험

**클라이언트에서 계산한 예상금액을 서버가 믿으면 안 됩니다.**

```
❌ POST /api/order { expectedAmount: 682000 }  → 서버가 그대로 사용
✅ POST /api/order { stockCode, qty }          → 서버가 시세를 다시 조회해 계산
```

브라우저에서 온 값은 조작될 수 있습니다. **⑤에서 서버가 시세를 다시 조회하는 것은 중복이 아니라 검증입니다.**

## 4. 흐름 E — 회고

```
브라우저                Server Component      Supabase        KIS
   ├─ GET /journal ────────>│                    │             │
   │                        ├─ orders ⨝ rationales (user_id 필터) ─>│
   │                        │<─ 내 최근 n건 ──────────┤         │
   │                        ├─ 종목별 현재가 조회 ─────────────>│
   │                        │<─ 현재가 ────────────────────────┤
   │<─ HTML (표 + 집계) ────┤
   │
   │  [당시가 vs 현재가 대조 표 — 여기까지 AI 없음]
   │
   ├─ [내 근거 되돌아보기] 클릭
   ├─ POST /api/ai/review ─>│                            Gemini
   │                        ├─ 최근 20건 근거 목록 ──────────>│
   │                        │<─ 회고 코멘트 4문장 ────────────┤
   │                        ├─ logEvent(journal_reviewed) ─>│
   │<─ 코멘트 ──────────────┤
```

### 🔴 KIS 현재가 조회를 실패해도 화면이 나옵니다

```
현재가 조회 성공 → 당시 68,000원 → 현재 71,200원 (+4.7%)
현재가 조회 실패 → 당시 68,000원 → 현재 —
```

**회고 화면은 저장된 데이터만으로도 성립합니다.** KIS와 Gemini가 모두 죽어도 근거 목록과 집계는 보입니다.

> 🔴 **그래서 회고 화면이 발표 시연의 최종 안전판입니다.** 다른 모든 것이 실패해도 이 화면 하나로 "이 서비스가 무엇을 하는지"를 보여줄 수 있습니다.

## 5. 실패 전파 정리

| 실패 지점 | 전파 범위 | 사용자에게 보이는 것 |
|---|---|---|
| Gemini | 해당 AI 영역만 | 숫자·표는 그대로, AI 자리에 재시도 버튼 |
| KIS 시세 | 해당 종목만 | "시세를 불러오지 못했습니다" + 주문 폼 비활성화 |
| KIS 토큰 | 계좌·시세·주문 전부 | "계좌 정보를 불러오지 못했습니다" + 회고 화면은 정상 |
| Supabase | 검색·주문·회고 | "기록을 불러오지 못했습니다" |
| 로그인 안 함 | 주문만 | Google 로그인 버튼 (조회·회고는 그대로 열람 가능) |
| 가상 예산 초과 | 주문만 | 남은 한도 안내 + 회고 화면 링크 |

**어느 칸에도 "화면이 하얗게 됨"이 없어야 합니다.** ([[../05_Scope/02_definition_of_done|완료 기준]] REQ-05 항목)

## 6. 이 문서에서 확정한 설계 결정 5가지

| # | 결정 | 근거 |
|---:|---|---|
| 1 | AI 호출을 별도 왕복으로 분리 | AI 실패가 화면을 깨뜨리지 않게 (REQ-05) |
| 2 | 근거 저장이 KIS 주문보다 앞 | 주문이 실패해도 근거는 남아야 함 |
| 3 | 예상금액을 서버가 재계산 | 클라이언트 값은 신뢰하지 않음 |
| 4 | 가상 예산 검증이 실제 계좌 검증 뒤, KIS 호출 전 | 로그인 사용자별 한도로 계좌 1개를 안전하게 공유 |
| 5 | 회고 화면은 외부 API 없이도 렌더링 | 시연 안전판 확보 |
