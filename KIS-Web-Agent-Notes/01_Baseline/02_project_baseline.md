## 2. 프로젝트 목적

사용자가 자신의 매매 판단 근거를 **기록하고, 모아 보고, 설명할 수 있게** 합니다.

수익을 내게 하는 것이 목적이 아닙니다. 종목을 추천하는 것도 목적이 아닙니다.

---

## 3. 문제 정의

```
모의투자를 시작한 초보 투자자는 매수 시점에는 나름의 이유가 있지만,
그 이유가 어디에도 남지 않아 며칠 뒤에는 자신이 왜 샀는지 설명하지 못합니다.
설명하지 못하면 그 판단이 옳았는지 틀렸는지도 배울 수 없습니다.
```

증거 아닌 것과 증거인 것을 구분합니다.

| 구분 | 내용 |
|---|---|
| 사실 | KIS 앱과 증권사 앱은 주문 내역을 보여주지만 **주문 사유 필드가 없습니다** |
| 해석 | 사유가 없으므로 회고가 감(感)에 의존하게 됩니다 |
| 가정 | 사유를 남기면 회고가 가능해집니다 → **이 프로젝트가 검증하려는 가정** |

## 4. 프로젝트 범위 초안

### 포함

| # | 범위 |
|---|---|
| 1 | ~~KIS 모의투자 계좌 **잔고 조회**~~ 🔄 **내 주문 집계 + 가상 예산** + AI 해석 |
| 2 | 종목 시세 조회 + AI 해석 |
| 3 | ~~매수 주문~~ 🔄 **매수·매도 주문** (근거 입력 필수) |
| 4 | 판단 근거 회고 화면 + AI 코칭 |
| 5 | Vercel 공개 배포 |

> 🔄 **1번이 계획과 가장 크게 달라진 항목입니다. 계좌 화면(`/`)은 KIS 잔고를 쓰지 않습니다.**
>
> 모의계좌 1개를 여러 방문자가 나눠 쓰기 때문에, 계좌 잔고에는 **다른 사람의 주문과 서비스 이전부터 있던 종목이 섞여 있습니다.** 그것을 "내 계좌"로 보여주면 사용자가 **사지도 않은 종목을 자기 것으로 읽습니다.** 그래서 보유 수량·평단가·평가손익·남은 예산을 전부 `orders` 집계 + `user_wallets`로 만듭니다(`lib/portfolio.ts`, `app/api/account/route.ts`). KIS는 **보유 종목의 현재가**를 받아오는 데만 씁니다.
>
> **KIS 잔고를 아예 안 쓰는 것은 아닙니다.** 매수 주문 직전의 실제 예수금 검증(`getBuyableCash`, 예외 2.5)은 지금도 KIS에 물어봅니다. 가상 예산이 1차 방어선, 실제 예수금이 최종 방어선이라는 2단 구조는 계획대로 남아 있습니다(9절 아래 [[../02_Domain/02_user_roles\|사용자 역할]] 4절).
>
> ⚠️ **`lib/kis.ts`의 `getAccountBalance()`는 호출부가 0건인 죽은 코드입니다.** 이 표의 계획대로 잔고 화면을 만들려고 먼저 짰다가, 위 이유로 화면 설계를 바꾸면서 쓰지 않게 됐는데 지우지 않았습니다.

### 5.3 🔴 서버리스 제약

Vercel의 Route Handler는 **요청마다 새로 뜨고 메모리를 공유하지 않습니다.** 프로젝트 2에서는 n8n이 계속 떠 있어서 성립했던 것이 여기서는 성립하지 않습니다.

| 항목 | n8n | Vercel |
|---|---|---|
| KIS 접근토큰 보관 | 워크플로우가 관리 | 🔴 **Supabase 테이블에 캐시 필수** |
| 호출 IP | 고정 (내 서버) | 🔴 **매번 다름** |
| 실행 시간 제한 | 없음 | ~~Hobby 기준 10초~~ 🔄 **기본 10초 · 라우트별로 늘릴 수 있음** |
| 스케줄러 | 있음 | 없음 (Cron 별도) |

이 표가 [[../04_Architecture/02_architecture|아키텍처]]와 [[../03_Data_Event/01_data_structure|데이터 구조]]의 주요 설계 근거입니다.

> 🔄 **"10초"는 기본값이었지 고정 상한이 아니었습니다.** `app/api/chart/route.ts`는 `export const maxDuration = 45`로 45초를 씁니다. 분봉 차트가 KIS 페이지를 여러 번 나눠 받아야 하는데, 앱키당 초당 1건 제한(`EGW00201`) 때문에 호출 사이를 큐로 띄우다 보니 10초 안에 못 끝냈기 때문입니다(`lib/kis.ts`).
>
> **제약이 사라진 게 아니라 값을 올려 피한 것**이고, **나머지 라우트는 전부 기본값 그대로**입니다. 주문(`/api/order`)은 손대지 않았습니다 — 주문 경로가 45초를 필요로 한다면 그건 늘릴 게 아니라 설계를 의심할 신호입니다.
>
> 🔴 **"스케줄러 없음"은 끝까지 유효했고, 실제로 설계를 한 번 갈랐습니다.** 8/7에 체결 조회가 들어올 때 "스케줄러로 자동 감시"가 아니라 **사용자 버튼 트리거**를 고른 이유가 이 줄입니다(4절 제외 4번).

## 6. 🔴 대안 시나리오 — KIS 연결이 막힐 경우

Day 1의 첫 작업은 **Vercel 배포본에서 KIS 토큰 발급이 되는지 확인**하는 것입니다. 여기서 막히면 4일이 통째로 위험합니다. 그래서 판단 시점과 대안을 미리 정합니다.

```
판단 시점: 8/7(금) 12:00
조건:     Vercel 배포 URL에서 KIS 잔고 조회가 성공하지 못했다
```

### 대안 A — KIS를 모의 데이터로 대체

| 유지 | 대체 |
|---|---|
| 화면 3개, 근거 입력 강제, 회고 화면, AI 3종, Supabase, Vercel | 계좌·시세를 **고정 시드 데이터**로 대체 |

요구사항 REQ-01~05는 **전부 그대로 만족합니다.** KIS는 요청서 요구사항이 아니기 때문입니다. 발표에서 "외부 API 연동은 배포 환경 제약으로 시드 데이터로 대체했다"고 명시합니다.

### 대안 B — KIS 호출만 별도 경유

n8n 워크플로우를 웹훅으로 열어 두고 Next.js가 그것을 호출합니다. IP가 고정되므로 문제가 해소됩니다.

> 대안 B는 **대안 A보다 뒤에 둡니다.** 구성 요소가 하나 늘고, 발표 시점에 n8n이 떠 있어야 하는 의존이 생기기 때문입니다.

**결정 원칙: 8/7 12:00에 판단하고, 그 이후에는 되돌리지 않습니다.**

### 🔴 서비스 role key 사용 (기획 대비 변경)

당초 "service role key 미사용"으로 기획했으나(§9, [[../03_Data_Event/01_data_structure|데이터 구조]] §7), 실제 구현 중 `kis_tokens`·`event_logs`처럼 **로그인 여부와 무관하게 서버만 써야 하는 테이블**은 anon key + RLS만으로 막을 방법이 없다는 것을 확인했습니다. `lib/supabase/admin.ts`에 **서버 전용** service role 클라이언트를 두고 씁니다.

> 🔄 ~~"이 두 테이블에만 사용합니다"~~ **이 서술은 부정확했습니다.** 실제 사용처는 **5곳**이고, 대상 테이블도 두 개가 아닙니다.

| 사용처 | 대상 | 세션 키로는 왜 안 되는가 |
|---|---|---|
| `lib/events.ts` | `event_logs` | 정책이 없어 접근 자체가 막힙니다. **토큰 갱신 실패처럼 로그인 이전 단계의 이벤트**도 기록해야 합니다 |
| `lib/kis.ts` (3곳) | `kis_tokens` | 동일. **미로그인 방문자도 시세를 봐야 하므로** 세션이 아예 없을 수 있습니다 |
| `app/api/order/route.ts` | 🆕 **`user_wallets` upsert** | 예산 지급은 서버만 해야 하므로 `insert`·`update` 정책을 **일부러 두지 않았습니다**(브라우저가 자기 예산을 조작하는 것을 막기 위함) |
| `app/api/ai/explain/route.ts` | 🆕 **`stocks` 조회** | 공개 데이터라 세션 키로도 됩니다. admin 클라이언트를 재사용한 것뿐 — **줄일 수 있는 부분** |
| `app/api/disclosures/route.ts` | 🆕 **`stocks` 조회** | 동일 |

~~`orders`·`rationales`·`user_wallets`는 원래 설계대로 사용자 세션(anon key + `auth.uid()` RLS)으로 씁니다.~~ 🔄 `orders`·`rationales`는 원래 설계대로 사용자 세션으로 씁니다. **`user_wallets`는 읽기만 세션 키이고 쓰기(첫 주문 시 예산 지급)는 admin입니다** — 이것도 절반만 맞는 서술이었습니다.

> 🔴 **정정 노트 자체가 틀렸던 이유를 남겨둡니다.** 이 노트는 admin 클라이언트를 처음 만들 때(토큰·이벤트 두 곳) 적었고, 그 뒤 `user_wallets`·`stocks`로 사용처가 늘어날 때마다 **코드만 늘고 이 문장은 갱신되지 않았습니다.** "예외를 문서에 적었다"는 사실이 "그 예외가 그대로 유지된다"를 보장하지 않습니다.
>
> **위험 크기와 발표에서 말할 내용**은 [[../03_Data_Event/01_data_structure|데이터 구조]] 7절에 정리돼 있습니다. 요점만 옮기면, 키가 새는 경로는 없고(서버 환경변수 전용, `NEXT_PUBLIC_` 아님) **문제는 서버 코드에 버그가 생겼을 때 RLS가 막아주지 못한다는 것** — 방어선이 2겹에서 1겹이 됩니다.
