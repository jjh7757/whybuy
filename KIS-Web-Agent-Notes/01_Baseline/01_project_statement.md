## 2. 프로젝트 한 문장

```
모의투자를 시작한 초보 투자자가
매수 버튼을 누른 이유를 며칠 뒤에 설명하지 못하는 문제를
KIS 모의투자 계좌 데이터와 판단 근거 기록을 한 화면에 모은 웹 서비스로 줄여
자신의 매매 근거를 목록으로 되돌아보고 설명할 수 있도록 합니다.
```

> 🔄 **"매수 버튼"이라는 표현은 그대로 둡니다.** 8/7에 매도 주문이 들어오면서([[../05_Scope/01_mvp_scope\|MVP 범위]] 4.2d절) 실제로 기록·회고되는 것은 **매수 근거와 매도 근거 양쪽**이 되었습니다. 매도도 완전히 같은 구조입니다 — 근거를 고르지 않으면 주문 버튼이 눌리지 않고, `rationales` 행이 남고, 회고 화면에 매수와 나란히 쌓입니다.
>
> **그런데도 문장을 고치지 않는 이유**는, 이 프로젝트가 풀려는 문제가 처음부터 "매수"라는 **특정 행위**가 아니라 **"자기 판단을 며칠 뒤에 설명하지 못한다"는 상태**였기 때문입니다. 매도는 그 문제의 **범위가 넓어진 것**이지 문제가 달라진 것이 아닙니다. 문장을 "매매 버튼"으로 다듬으면 매끄러워지지만, 이 기획이 어디서 출발했는지가 지워집니다.

### 문장 구조 확인

| 요소 | 내용 |
|---|---|
| 누가 | 모의투자를 시작한 초보 투자자 |
| 어떤 문제 | 매수한 이유를 나중에 설명하지 못한다 · 🔄 **매도 이유도 동일한 구조로 기록·회고됩니다** (8/7 추가) |
| 어떻게 | 주문 직전에 근거 입력을 강제하고, 근거를 회고 화면에 누적 |
| 어디까지 | 자기 매매 근거를 목록으로 되돌아보고 설명할 수 있는 상태 |

## 3. 프로젝트 2에서 문제 정의를 옮긴 이유

프로젝트 2의 문장은 이랬습니다.

```
투자용어와 계좌 화면을 해석하지 못해 매매 판단을 내리지 못하는 문제
```

이번에는 **"판단을 내리지 못한다"에서 "판단을 기억하지 못한다"로 초점을 옮겼습니다.**

| | 프로젝트 2 (텔레그램) | 프로젝트 3 (웹) |
|---|---|---|
| 초점 | 매매 **직전**의 이해 | 매매 **이후**의 회고 |
| 핵심 화면 | 대화 1턴 | 근거 목록 |
| 성공 확인 | "왜 샀는지 말할 수 있는가"를 사람이 물어봄 | **화면에 근거 목록이 남아 있고 사용자가 그것을 보며 설명함** |

### 왜 옮겼습니까?

프로젝트 2의 성공 기준은 `사용자가 매매 근거를 설명할 수 있는가`였고, 이것을 **사람이 직접 물어보는 방식**으로만 확인할 수 있었습니다. 텔레그램에는 근거를 모아 보여줄 자리가 없었기 때문입니다.

웹에는 그 자리가 있습니다. 회고 화면 자체가 성공 기준의 증거물이 됩니다. **측정 방법이 바뀌었으므로 문제 정의도 그에 맞춰 옮겼습니다.**

## 4. 🔴 웹이기 때문에 가능해진 것 (REQ-01 필수 항목)

프로젝트 요청서는 n8n으로 만든 것을 웹으로 옮길 경우 **웹이기 때문에 가능해진 것**을 요구합니다. 5가지입니다.

### 4.1 근거 히스토리 회고 화면

| | 텔레그램 | 웹 |
|---|---|---|
| 20턴 전 근거 확인 | 스크롤로 찾아야 하고 사실상 불가능 | 목록 화면 한 번 |
| 근거 유형별 비교 | 불가능 | 정렬·필터·집계 |
| "그냥 감" 비율 확인 | 불가능 | 화면에 숫자로 표시 |

**이것이 이 프로젝트의 존재 이유입니다.** 대화형에서는 성공 기준을 사람이 물어봐야 확인할 수 있었지만, 웹에서는 사용자가 스스로 확인합니다.

### 4.2 주문 4턴 → 1화면

프로젝트 2의 흐름 문서는 이렇게 시작했습니다.

> 일반적인 웹 서비스는 화면이 상태를 들고 있습니다. 이 프로젝트는 화면이 없고 대화가 화면입니다.

**웹으로 오면서 이 비용이 사라집니다.**

| 대화형이 필요로 했던 것 | 웹에서 | 절감 |
|---|---|---|
| 의도 분류 (자연어 → 요청 종류) | 화면의 버튼이 의도를 확정 | -4h |
| `conversation_context` 테이블 (`그거`의 해석) | 화면이 종목을 들고 있음 | 테이블 1개 삭제 |
| `awaiting_confirmation` / `awaiting_rationale` 대기 상태 | 폼 제출 1회로 압축 | 상태 3개 삭제 |
| `expires_at` 만료 정리 | 화면을 닫으면 끝 | -1.5h |
| 중복 주문 부분 유니크 인덱스 | 제출 버튼 비활성화 + 서버 재검증 | 단순화 |

**절감한 시간을 회고 화면과 AI 코칭에 씁니다.** 기능을 옮긴 것이 아니라 **비용 구조가 바뀐 것을 이용해 다른 기능을 넣은 것**입니다.

### 4.3 근거와 결과의 대조

`저평가라고 판단` → 그때 가격 68,000원 → 지금 71,200원.
이 대조는 **표와 색상이 있어야 읽힙니다.** 텔레그램 텍스트 메시지로는 3건만 넘어가도 읽을 수 없습니다.

### 4.4 링크 하나로 접속

텔레그램 봇은 상대가 봇을 검색해 `/start`를 눌러야 합니다. 웹은 URL 하나면 됩니다. REQ-04가 요구하는 "링크를 받은 사람이 아무 설치 없이 바로 쓸 수 있어야 한다"는 조건은 **텔레그램으로는 원리적으로 만족할 수 없었습니다.**

### 4.5 근거 미입력 시 주문 불가를 UI로 강제

대화에서는 사용자가 근거 질문에 답하지 않고 그냥 나갈 수 있었습니다(예외 흐름 2.8). 웹에서는 **근거를 고르지 않으면 주문 버튼이 비활성화**됩니다.

> 이 차이로 **근거 기록률이 측정 지표에서 구조적 보장으로 바뀝니다.** 프로젝트 2의 지표 1번이 프로젝트 3에서는 100%가 확정입니다. 그래서 성공 기준을 회고 쪽으로 옮겼습니다.

## 5. 성공 기준

**사용자가 회고 화면을 보며 자신의 과거 매매 근거를 설명할 수 있는가.**

### 측정 방법

| 측정 항목 | 확인 방법 | 목표 |
|---|---|---|
| 근거 기록률 | ~~`rationales` 행 수 ÷ `orders` 중 `submitted`+`rejected` 행 수~~ 🔄 **근거가 연결된 `orders` 행 수 ÷ 내 `orders` 전체 행 수** (상태 필터 없음) | **100%** (UI로 강제) |
| `gut`(그냥 감) 비율 | `reason_type = 'gut'` 비율 | 참고치. 낮을수록 좋음 |
| 메모 작성률 | `reason_memo`가 비어 있지 않은 비율 | 참고치 |
| 회고 설명 가능성 | 테스트 사용자 2명에게 회고 화면을 보여주고 "이건 왜 샀나요?" 질문 | **주된 기준** |

> 🔄 **`submitted`+`rejected`로 거르면 안 되는 상태가 됐습니다.** 계획 시점의 `orders.status`는 이 2가지뿐이라 "전체"와 같은 뜻이었지만, 8/7에 지정가 주문이 들어오며 상태가 5종(`requested`/`filled`/`submitted`/`cancelled`/`rejected`)으로 늘었습니다([[../03_Data_Event/01_data_structure\|데이터 구조]] 2절). 그대로 두면 **체결된 주문(`filled`)과 취소한 주문(`cancelled`)이 통째로 분모에서 빠집니다.** 실제 화면(`app/journal/page.tsx`)은 상태를 보지 않고 내 주문 전체 행으로 셉니다.
>
> **원칙 자체는 그대로입니다.** 근거는 KIS 호출보다 **먼저** 저장하므로(`app/api/order/route.ts`), 주문이 어떤 상태로 끝나든 근거 행은 남습니다. 상태를 볼 이유가 애초에 없었던 것이고, 계획의 조건은 "상태가 2개뿐"이라는 우연에 기대고 있었습니다.
>
> ⚠️ **[[../03_Data_Event/01_data_structure\|데이터 구조]] 10절의 측정 SQL 1번에는 옛 조건(`status in ('submitted','rejected')`)이 아직 남아 있습니다.** 발표에서 숫자를 뽑을 때는 화면 쪽 계산을 기준으로 씁니다.

### 성공 기준으로 쓰지 않는 것

| 제외 항목 | 이유 |
|---|---|
| 수익률 | 시장에 좌우되고 4일 안에 검증 불가. 문제 정의와 층위가 다름 |
| 주문 건수 | 많이 사는 것이 목적이 아님 |
| 체결 여부 | 성공 기준과 무관. ~~범위에서 제외 (`Won't`)~~ 🔄 **기능으로는 8/7에 들어왔습니다** — 아래 참고 |

> 🔄 **"성공 기준으로 쓰지 않는다"와 "만들지 않는다"를 한 줄에 섞어 적은 것이 문제였습니다.** 뒤쪽은 뒤집혔고, 앞쪽은 그대로입니다.
>
> - **뒤집힌 것**: 지정가 주문을 넣으면서 "주문 접수 = 체결"이라는 전제가 깨져 체결 조회가 **전제 조건**이 됐습니다([[../05_Scope/01_mvp_scope\|MVP 범위]] 4.2c절). 지금은 `orders.filled_qty`·`filled_price`가 쌓이고, 계좌 화면의 보유 수량·평단가·평가손익이 **전부 이 값을 씁니다**(`lib/portfolio.ts`).
> - **그대로인 것**: **체결 건수·체결률을 이 프로젝트의 성공 척도로 삼지 않습니다.** 체결은 시장이 정하는 것이고, 검증하려는 것은 "사용자가 자기 근거를 설명할 수 있는가"입니다. 지정가가 하루 종일 안 체결돼도 근거는 남고 회고는 성립합니다.

## 7. 확인이 필요한 가정

| 가정 | 검증 시점 | 실패 시 |
|---|---|---|
| 🔴 **Vercel(고정 IP 없음)에서 KIS API를 호출할 수 있다** | Day 1 첫 2시간 | [[02_project_baseline\|기준선]] 6절 대안 시나리오 |
| 근거를 강제로 적게 하면 사용자가 이탈하지 않는다 | Day 3 테스트 사용자 2명 | 근거를 선택형만으로 축소 |
| 회고 화면을 보면 과거 판단을 설명할 수 있게 된다 | Day 4 정성 확인 | 발표에서 미검증 가정으로 명시 |
| ~~근거 선택지 6개~~ 🔄 **선택지 11개**(매수 6 + 매도 5)가 실제 판단을 담기에 충분하다 | `gut` 비율로 확인 | 발표에서 한계로 설명 |

> 🔄 **1번 가정은 Day 1(8/6) 오후에 통과했습니다.** 고정 IP 없이도 KIS 호출이 됐고, 대안 시나리오 A·B는 발동하지 않았습니다. **대신 가정 목록에 없던 것이 터졌습니다** — 앱키당 초당 1건 제한(`EGW00201`). "연결이 되는가"만 가정으로 잡았고 "얼마나 자주 부를 수 있는가"는 잡지 않았습니다. 경위는 [[../07_Submit/02_scope_reduction\|범위 축소 설명서]] 7절에 있습니다.
>
> 🔄 **근거 선택지는 6개에서 11개가 됐습니다.** 8/7에 매도 근거 5종(손절·익절·목표가 도달·판단이 바뀜·그냥 감)이 추가됐습니다(`lib/rationale.ts`). 정확히는 **화면에 뜨는 선택지가 11개**이고, `gut`을 매수·매도가 공유하므로 **서로 다른 `reason_type` 값은 10개**입니다.
>
> ⚠️ **가정 자체는 여전히 미검증입니다.** 선택지가 늘었다고 "충분해졌다"고 말할 수 없고, `gut` 비율로 확인하려던 표본은 4일치라 통계가 아닙니다([[../05_Scope/01_mvp_scope\|MVP 범위]] 8절).
